# APA AC29: автоматический выбор групповой команды по запросу

## Новая работающая возможность

Один вход `apa-native-group-request/1` распознаёт действие в русском/английском запросе и выбирает уже принятый нативный инструмент:

| Запрос | Выбранная команда | Существующий verifier |
|---|---|---|
| Сгруппировать выбранные колонны | CreateNativeGroupV1 | VerifiedNativeGroupCreate |
| Переместить целую группу | MoveNativeGroupV1 | VerifiedNativeGroupMove |
| Разгруппировать выбранную группу | UngroupNativeGroupV1 | VerifiedNativeGroupUngroup |

Путь: запрос + явные данные источника → распознавание → существующий typed adapter → fresh capability discovery → тот же Router/registry/SceneWriter → прежние readback/save/reopen правила. Публичные entrypoint `prepare_auto_optimized_native_task` и `prepare_current_runtime_group_native_task` принимают новый вход. Нового Router, исполнителя, языковой модели или зависимости нет.

GUID участников, Group GUID, источник и вектор не придумываются из текста. Для создания Group GUID/translation должны быть null; для перемещения нужны точная группа и ненулевой горизонтальный вектор; для разгруппировки вектор запрещён. Составные/неоднозначные/булевы запросы отклоняются. Копирование с размещениями продолжает использовать существующий mass-request вход; просьба «скопировать группу» без размещений не получает случайные координаты.

## Реальная квалификация текущего AC29 — только чтением

Код установлен в действующий APA из `22bd5092ac1e2a91f0fc1f0c1a3a82fb573bf900`. На текущей принятой копии188GUID (savedSHA `ebbd057418099a0823e2dd58a9765fd25ab6e41de6524253ad0785764c288187`) три запроса прошли:

1. Распознавание и получение единственной нужной команды.
2. Реальную проверку регистрации выбранной команды и точной SDK runtime identity AC29.
3. Чтение фактических источников: несгруппированные Column либо полный состав существующей группы.
4. Проверку code-owned source verifier, точных GUID участников/сегментов, сохранённой модели и границ scope.
5. Для переноса — также проверку свободного целевого BREP.

На создание/разгруппировку scope содержит2физических участника,186сохранённых GUID; на перенос —4GUID участников/сегментов и184сохранённых. Выбран ровно1native operation в каждом графе. SHA/контрактов/параметров сохранены в квитанции.

`nativeCommandExecutions=0`, `nativeWriteAttempts=0`, `saveCalls=0`, SQLite не создавалась. Это фактическая native **READ_ONLY** квалификация нового выбора, не новый LIVE_WRITE_PASS. Доказательства самих исполнителей с записью/сохранением/переоткрытием переиспользованы из PR185/186/188. Принятые операции не повторялись.

## Установка и автоматические проверки

Изменены только два тела существующих функций ядра, добавлен нормализатор. Прочие части ядра,296 исходных контрактов,30 файловых/4semantic команды, новый DXF адаптер и три принятых групповых verifier сохранены. Резервная копия ядра сохранена. APX, зависимости, исходные PLN и main не менялись.

Автоматические проверки нового распознавания включены в CI Windows3.11/3.12. Проверены три действия, русские/английские формы, отсутствие мутации входа, неполные/составные/булевы запросы и невозможность получить dispatchable preview без свежей регистрации. Точные CI статусы в `ci-checks.json`.

Границы: распознаются три явно поддержанных групповых действия, а не произвольный свободный текст. Действуют прежние узкие контракты исполнителей для плоских Column групп; поддержка других типов не объявляется принятой этим результатом. Пользовательский запрос не заменяет разрешение на конкретный PLN и scope.

Доказательства: `native-readonly-qualification.json`, `independent-audit.json`, `deployment.json`, `ci-checks.json`, `artifact-sha256.json`. Полные исходные дампы остаются локально. Реестр `APA-P70.A11.S21`.
