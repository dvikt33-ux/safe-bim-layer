# Architectural AI checkpoint 14 — deeper reuse audit: requirements, openBIM state, simulations and engineering

Date: 2026-10-08
Status: ACTIVE RESEARCH CHECKPOINT
Branch: feature/working-archicad-mvp
Current implementation target: Archicad 29 only

## Executive conclusion

The custom-code surface shrank again.

This pass found mature or near-mature solutions for several areas that were still at risk of becoming custom SBIM subsystems:

- BIM information requirements / EIR-BEP / software templates / validation-rule export: **BIMQ**
- openBIM model state / versioning / object queries / API / controlled edit sessions: **Qonic**
- model + specification linking and decision rationale: **NBS Chorus**
- CDE / issues / documents / audit trail / webhooks / MCP: **Catenda Hub**
- open semantic/topology/property-time standards: **IFC + bSDD + BOT + OPM + BCF + openCDE**
- environmental/daylight/energy analysis: **Ladybug Tools / Honeybee**
- structural analysis handoff and automation: **Archicad SAF + external FEA, notably Dlubal API**
- MEP calculations and sizing: **Archicad 29 MEP Designer**
- collision checking: **Archicad built-in Collision Detection + native C++ collision API**
- product/manufacturer content: **BIMobject + BIMLIB**
- generic compliance/independent QA: **Solibri / IfcOpenShell / IDS**, already identified earlier

The resulting SBIM should be designed as an **integration and semantic kernel** around these existing systems, not as a replacement for them.

# 1. BIMQ — much closer to our template/information-requirement problem than previously recognized

## Confirmed capabilities

BIMQ is not just a model checker.

Its current product explicitly manages:
- information requirements;
- EIR/BEP-style project requirements;
- phases, purposes/use cases and actors;
- central attribute requirements;
- model-component requirements;
- uniform IFC mappings across authoring tools;
- software templates for Archicad, Revit, Allplan and ProVI;
- validation/test rules for IDS, Solibri, BIMcollab ZOOM, DESITE MD PRO, simplebim and mvdXML;
- Excel/PDF requirement exports;
- IDS import and synchronization;
- IFC reference-model import to derive enumerations/ranges.

The 2026 update can analyze IFC objects and translate their attributes into allowed enumerations/value ranges.

A freely accessible high-rise/building catalogue exists with standard mappings to:
- IFC2x3;
- IFC4;
- Archicad;
- Revit;
- Allplan;

and contains architectural, structural, HVAC, electrical and FM-oriented information requirements.

## Public API audit

The public repository `AEC3-Deutschland-GmbH/BIMQ-API` provides an OpenAPI definition.

Verified endpoints include read access to:
- projects/contexts;
- actors;
- models;
- mappings;
- phases;
- purposes;
- milestones;
- data drops;
- concepts;
- concept trees;
- required concepts;
- map items;
- IFC requirements;
- mvdXML;
- DESITE rules.

Authentication uses OAuth 2.0 Authorization Code + PKCE. Client IDs must be registered with AEC3.

Current public API is primarily **read-side**. It is not evidence of a complete remote authoring API.

## Why this matters to our Archicad 29 template

Before continuing to manually invent:
- every project property;
- every data requirement;
- every IFC mapping;
- every discipline/phase-specific information matrix;
- every checker rule;

we should test whether BIMQ can generate a large part of the base information architecture and Archicad-side template artifacts.

This may become the **requirements compiler upstream of TDK_AC29.tpl**.

Potential flow:

```
Russian/office project requirements
        ↓
BIMQ requirement catalogue
        ↓
Archicad attribute/template export
        ↓
IFC mapping
        ↓
IDS/Solibri rules
        ↓
TDK_AC29.tpl
```

## Access

BIMQ currently offers a 30-day full-function trial.

Its Free package is limited, but the product has been explicitly designed for educational/standards use; institutional/education access must be checked directly.

### Decision

**P0 TEST BEFORE FURTHER CUSTOM INFORMATION-SCHEMA WORK.**

Questions:
1. Exact Archicad 29 template/attribute export format?
2. Does export preserve Archicad 29 classifications/properties cleanly?
3. Can Russian project requirements/classifications be imported in bulk?
4. Can our canonical Rule IDs be stored and round-tripped?
5. Can IDS generated by BIMQ encode all the informational checks we need?
6. Can BIMQ coexist with our project template-builder rather than replacing it?
7. What API/export rights exist for a student/education account?

# 2. Qonic — strong candidate for the openBIM shadow state / version layer

## Current product

Qonic positions itself as an agentic BIM platform for:
- modeling;
- coordination;
- model querying;
- quality checking;
- quantities;
- drawings;
- clash resolution;
- IFC delivery;
- geometry creation through its product UI/agents.

Its current AI claims it can compare changes and fix them directly with an edit receipt.

## Free plan

The current Free plan provides:
- portfolio up to 5,000 m²;
- unlimited users/viewers;
- one active project;
- five models;
- viewing;
- modeling;
- one week version history;
- reports and default libraries.

This is enough for a serious technical prototype on a small test project.

## Public API

The public v1 API is unusually useful:
- base URL `https://api.qonic.com/v1`;
- OAuth 2.1 Authorization Code + PKCE;
- scopes such as `projects:read/write`, `models:read/write`;
- projects;
- models;
- products/attributes;
- materials;
- spatial locations;
- codifications;
- types;
- custom properties;
- asynchronous jobs;
- viewer interaction;
- model import/export.

Most important: **external modification sessions**.

API flow:
1. start a model modification session;
2. perform grouped modifications;
3. end/publish/discard;
4. publish a new public model version.

Property changes are atomic at request level: invalid modification sets can be rejected without partial write.

## What this may replace

Qonic can potentially replace or reduce our custom work for:
- openBIM shadow representation;
- object/property querying;
- revision storage;
- external controlled edit sessions;
- version comparison;
- issue/quality workflows;
- generic model state outside Archicad.

Qonic's own implementation keeps changes internally and batches them into versions that can be published, discarded or reverted.

## Important gaps

For SBIM/AC29:
- no native Archicad round-trip plugin was verified;
- Archicad therefore connects through IFC today;
- Revit has a direct Qonic plugin;
- API property write is verified;
- public API geometry creation/editing is **not yet proven** even though Qonic UI/agents can create geometry;
- Free-plan API entitlement still needs a hands-on test;
- one-week Free version history is too short for project authority.

### Decision

**P0 FREE PROTOTYPE CANDIDATE**, but as a shadow/openBIM state, not Archicad 29 execution authority.

Test:
`Archicad 29 -> IFC -> Qonic -> API queries/edits/version -> IFC -> comparison`.

If reliable, Qonic may eliminate a large amount of custom project-state/version tooling.

Catenda Hub already provides:
- federated IFC;
- BCF issues;
- document control;
- approvals;
- ISO 19650 workflow;
- tamper-evident audit trail;
- REST API;
- webhooks;
- OpenCDE/BCF 3.0 APIs;
- MCP server for AI agents;
- IFC from Archicad/Revit/Tekla and others;
- exportable/open project data.

The current Catenda site explicitly says an AI agent can access project information through MCP using the user's permissions.

This overlaps strongly with our planned:
- project-data control plane;
- issue store;
- change/audit history;
- document links;
- MCP bridge for project context.

## Economic fit

Current pricing is project-value based:
- ~€400/month example for €10M project;
- ~€1,100/month for €50M project.

Therefore it is **not a sensible immediate solo/student MVP dependency**.

### Decision

- **DO NOT IMPLEMENT A GENERAL CDE**.
- For solo AC29 MVP: use cheaper/free components.
- Keep Catenda as the office/project-scale future path and architecture reference.
- Prefer openCDE/BCF-compatible internal boundaries so migration to Catenda or another CDE remains cheap.

# 4. NBS Chorus — model ↔ specification ↔ decision rationale is already a mature pattern

NBS provides an Archicad plugin that directly links Archicad model elements to structured specification clauses.

The workflow:
1. connect model to specification project;
2. assign clause references to model objects;
3. coordinate changes;
4. detect/update stale or inconsistent references.

NBS Chorus also provides:
- structured specification clauses;
- reusable master specifications;
- organization knowledge;
- early-stage specification;
- project decision notes;
- revision/change notifications;
- manufacturer product data.

The `Specification Notes` concept explicitly records:
- why a clause was parked;
- a design preference;
- health/safety requirements;
- an audit trail of decisions.

This is a mature implementation of part of what we called:
- Design Intent;
- decision rationale;
- project specification graph.

## Russia fit

NBS content is primarily UK/other supported content sets, so it is not our Russian regulatory corpus.

But its **information architecture** is directly reusable as a reference:
`ModelElement ↔ SpecificationClause ↔ DecisionNote ↔ Revision`.

A Russian implementation can use:
- TechExpert requirements/TPD;
- our canonical Russian requirement IDs;
- manufacturer data;

while borrowing NBS's linking/decision-rationale pattern.

### Decision

**REFERENCE / OPTIONAL PLUGIN**, not core Russian dependency.

Do not invent model-specification linking semantics without studying NBS in detail.

# 5. Open standards can replace a large custom Project Graph ontology

The buildingSMART standards server already exposes:
- IFC;
- IDS 1.0;
- BCF 3.0;
- openCDE Foundation API;
- openCDE Documents API;
- bSDD API;
- validation services.

bSDD has a public production API/Swagger and supports Class/Property retrieval from many dictionaries.

## W3C Linked Building Data ontologies

### BOT — Building Topology Ontology

BOT is specifically a minimal ontology for building topology:
- building;
- storey;
- space/zone;
- containment and building-component relationships.

### OPM — Ontology for Property Management

OPM is explicitly designed to represent **temporal properties that change as building design evolves**.

This is remarkably close to a part of our planned project-state graph.

## Revised Project Graph proposal

Do not create a universal SBIM ontology from blank classes.

Use a hybrid semantic layer:

```
IFC GUID/object identity
+
BOT topology
+
OPM temporal property state
+
bSDD semantic class/property URIs
+
BCF issues/decisions
+
IDS information requirements
+
OpenCDE project/document boundary
+
CUSTOM SBIM EDGES ONLY FOR:
    causal impact
    legal applicability
    design intent
    normative dependency
    structural/system criticality
```

This would radically reduce ontology invention and increase interoperability.

### Decision

**ADAPT STANDARD SEMANTICS; BUILD GAP ONLY.**

# 6. Environmental/daylight/energy analysis — use Ladybug Tools, not our own calculators

Ladybug Tools/Honeybee already provides free/open-source interfaces and SDKs around validated engines:
- Radiance — daylight/illuminance/glare/solar;
- EnergyPlus/OpenStudio — energy/HVAC/thermal;
- THERM/Window — assemblies/thermal bridges/condensation;
- OpenFOAM ecosystem where needed.

Honeybee supports:
- point-in-time and annual daylight;
- glare;
- electric lighting;
- energy;
- HVAC sizing;
- thermal comfort;
- microclimate;
- airflow;
- condensation risk;
- water use;
- passive/active strategies.

It exposes object-oriented SDKs and can be used through Grasshopper or standalone Python libraries.

For AC29:
- Rhino/Grasshopper Live Connection can provide one route;
- IFC/geometry adapters can provide another.

### Decision

**REUSE.**
Do not implement daylight, sun, energy, thermal-comfort or generic environmental solvers ourselves.

Our role:
- map Archicad/project geometry/materials into Honeybee/Ladybug;
- compile Russian project constraints into target metrics;
- interpret results and propagate them through Project Graph.

# 7. Structural analysis — Archicad already has the exchange model; external FEA already has APIs

Archicad 29's Structural Analytical Model and SAF workflow already support bidirectional exchange with structural analysis tools.

SAF translators cover:
- materials;
- cross-sections;
- local coordinate systems;
- curved wall handling;
- loads;
- import/export mappings.

Archicad Model Compare can compare imported/returned SAF models.

Dlubal RFEM/RSTAB currently exposes a gRPC API (API II):
- create/modify models;
- create loads;
- run calculations;
- read results;
- batch object transfer;
- documented as roughly 10x faster in communication than the older API I due to gRPC/batching.

### Decision

Do not build a generic structural FEA solver.

Use:
`Archicad Structural Analytical Model -> SAF -> FEA`.

For automation, evaluate Dlubal or another compatible solver with a usable API.

Our custom logic remains:
- when a design change invalidates a structural assumption;
- which analysis to trigger;
- how results bind back to project decisions;
- whether a change is acceptable.

# 8. MEP — Archicad 29 already provides more deterministic capability than we had been assuming

Archicad 29 MEP Designer currently supports system calculations and optimization.

Verified examples:
- ventilation flow/velocity calculations;
- Duct Size Optimizer;
- hydronic capacity/mass-flow/velocity;
- Hydronics Optimizer;
- water/wastewater and heating/cooling system support in System Browser;
- MEP Model Check.

Some calculation functions require Graphisoft cloud licenses.

### Decision

Before any custom MEP sizing/routing implementation:
1. inventory AC29 MEP Designer;
2. inventory AC29 MEP API;
3. use native system data where possible;
4. add external specialist tools only for missing engineering depth.

Our project graph should bind to native MEP systems rather than duplicate them.

# 9. Collision checking — another subsystem we must not rewrite blindly

Archicad 29 already has:
- built-in Model Check;
- Collision Detection;
- saved criteria sets;
- surface/volume tolerances;
- MEP/structure collision checks;
- headroom/accessibility clearance workflows;
- Issue creation from results.

The native C++ API exposes `ACAPI_Element_GetCollisions` for collision checks between GUID sets.

### Decision

For **live AC29 local collision checks**, native Archicad should be first choice.

Use Solibri/IfcOpenShell for independent/cross-model/release checking.

Only write custom spatial geometry checks when the required semantics cannot be expressed by:
- Archicad Collision Detection;
- model criteria;
- native collision API;
- Solibri;
- IfcOpenShell.

# 10. Product/manufacturer content — do not build a manufacturer catalogue

## BIMobject

BIMobject has public APIs with OAuth:
- Search API;
- product metadata;
- files/download;
- embedded previews;
- publishing APIs.

This can provide international product discovery/content.

## BIMLIB

BIMLIB currently exposes a Russian-market catalogue with more than 50,000 BIM models and discipline filters.

The catalogue includes current manufacturers/products and files for BIM authoring environments, including Archicad where the manufacturer provides that format.

BIMLIB's own live plugin is currently described mainly for Renga, so do not assume direct Archicad automation.

### Decision

Use product sources as **catalog adapters**, not a private copied product universe.

Canonical product record:
- manufacturer/product ID;
- source;
- current technical data;
- formats;
- classification;
- project-selected version;
- verification date.

# 11. Text2BIM source-code audit — its structure is directly reusable

The repository confirms a concrete multi-agent pattern:

- Product Owner prompt;
- Architect/floor-plan designer;
- Coder/tool executor;
- Reviewer/checker;
- Solibri rule checking;
- iterative correction.

Its Vectorworks integration defines a concrete list of modeling tools:
- wall create/height/thickness/style;
- windows/doors;
- move/delete;
- polygons;
- slabs;
- roofs;
- storeys;
- spaces;
etc.

This is not an Archicad solution, but it proves we should not invent our multi-agent orchestration from scratch.

## Important limitation

The implementation is comparatively straightforward/hard-wired:
- prompt-template files;
- explicit tool list;
- local state JSON;
- direct vendor API keys;
- fixed Solibri workflow paths.

That makes it a **method/code reference**, not a ready SBIM runtime.

### Decision

Borrow:
- role separation;
- deterministic checker feedback loop;
- tool-execution pattern;
- experiment/log structure.

Replace:
- hard-coded model selection;
- hard-coded paths;
- ad hoc project state;
- Vectorworks-specific tool layer.
