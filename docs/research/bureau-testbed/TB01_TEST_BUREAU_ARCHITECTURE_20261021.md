# ТБ-01 — испытательное автономное архитектурное бюро
**Статус:** R00 / спецификация и план испытаний, не установленная система. **Дата:** 21.10.2026.
**Программа:** «Собор 2026–27», организационная инфраструктура до начала новых тематических исследований; технологический спутник — APA/Archicad 29.
**Правило:** не изменять main, действующие чаты, PLN, Automa и рабочие процессы; не дублировать уже принятую работу.

## 0. Результат, который должен получить руководитель
Человек общается только с главным архитектором (ГАП), задаёт направление, получает объяснимую сводку и утверждает лишь принципиальные решения. ГАП самостоятельно составляет программу, распределяет задания директорам и сотрудникам, контролирует качество, направляет на независимый аудит, устраняет обычные сбои и докладывает о нерешённых ограничениях. Автономность не распространяется на необратимые изменения, расходы сверх лимита, предоставление новых прав, выбор участка/архитектурной концепции и изменение пользовательских приоритетов.

Цель испытания: доказать реальными событиями работу от намерения руководителя до проверенного итогового отчёта, а не только прохождение отдельных CI-тестов.

Ранее принятый APA worker PR #139 повторно используется по SHA. Зафиксированы блокировки UI и чатов и запрет повторной отправки с неизвестным результатом.
- Ранее документировались 19 адресатов: Д-01—Д-08, директора, секретариат, штаб и APA. Сквозной LIVE-доказательности автоматической передачи в ChatGPT по всем этапам ещё нет. Отдельный пилот Д-03 ограничен выбором вкладки без отправки сообщения.

## 2. Испытательные роли
1. Руководитель (человек) — направление, бюджет, стратегическое утверждение.
2. Главный архитектор / ГАП (агент) — единая точка доклада и делегирования.
3. Директор исследований (агент).
4. Директор технологий и APA (агент).
5. Исследователь первичных источников (агент).
6. Аналитик готовых решений (агент).
7. Аналитик программной структуры (агент).
8. Интегратор готовых инструментов (агент).
9. Независимый аудитор (агент, организационно выведенный из подчинения проверяемым директорам).
10. Секретариат (агент; не утверждает качество).
Итого **9 ИИ-ролей + руководитель**. Начинать с минимального подмножества ГАП + директор + исполнитель + аудитор + секретариат, наращивать только после базового PASS.

## 3. Два альтернативных способа верхнего управления — один победитель
**Вариант A: действующий PR #187** — интерфейс ChatGPT через Opera/Automa, существующая подтверждаемая очередь; проверять в отдельном фиктивном контуре, не на действующих чатах, с выключенной отправкой до ручной проверки.
**Вариант B: Paperclip** — отдельная «компания» ТБ-01, агенты и роли, цели, делегирование, учёт расходов, подтверждения, расписание/heartbeats; Codex/другие runtime-адаптеры только после проверки работающей авторизации и лимитов. Paperclip — control plane, не самостоятельная ИИ-модель и не база знаний.
**Запрет:** A и B не должны менять один job, получать один токен записи, отправлять в один чат или запускать один и тот же APA writer. Сопоставлять на одинаковом фиктивном входном пакете и неизменном критерии оценки.
**Решение:** оставить один control plane; второй — только наблюдение/функциональные подсистемы с явно заданным владельцем состояния.

## 4. Проверяемый набор готовых технологий и ответственность
| Компонент | Испытываемая роль | Обязательная граница |
|---|---|---|
| Paperclip | автономное управление агентами, назначения, согласования, heartbeats | эксперимент B, отдельная БД, отдельные runtime и бюджет |
| PR #187 | существующая очередь, точная доставка, сохранение контекста чатов | эксперимент A, без записи в боевые чаты |
| n8n | визуальная связка событий, публикаций, уведомлений и подтверждений | не создаёт второй список задач / управляющий цикл |
| RAGFlow | поиск по документам, первичные ссылки, конфликтные сведения | только тестовые копии с зафиксированными версиями |
| Dify | сравнительный кандидат вместо RAGFlow, не в общей боевой схеме параллельно | сопоставить на одинаковом наборе вопросов |
| Graphify | карта зависимостей исходников APA и ссылок из документов | сохранять EXTRACTED отдельно от INFERRED; исходная схема графа не является BIM |
| Spec Kit | требования -> план -> задачи -> анализ -> исполнение -> проверка | основной исследуемый процесс согласования |
| ECC / Superpowers | роли/навыки кодовых исполнителей (сравнение) | выбрать один набор правил, не накладывать оба без изоляции |
| REA / Joern | исследование поведения и структуры программ, статический граф кода | сначала собственные/разрешённые исходники, read-only; анализ чужих бинарников только при разрешении |
| IfcOpenShell / FreeCAD | независимая проверка IFC и геометрии | не считать заменой записи нативных PLN элементов |
| MiniZinc / OR-Tools | проверка ограничений компоновки | не менять фактическую архитектурную геометрию автоматически |
| Google Drive | документы, журнал решений, материалы для пользователей | файлы не исполняют задачи и не являются общей транзакционной очередью |
| GitHub | версия, квитанции, ревизия, draft PR, неизменяемые источники | секреты, адреса чатов, токены, личные данные не публиковать |

Платформы подключать через документированные интерфейсы и визуальные настройки, а не разработкой собственной платформы. Для каждой интеграции фиксировать владелец данных, интерфейс, политику ошибок, версию, лицензию, ресурсы, путь отката.

## 5. Единая модель информации
**Пять раздельных сущностей:**
- `DECISION`: решение руководителя, версия, полномочия и история изменений;
- `TASK`: поручение, источник, исполнитель, условие готовности, зависимости, срок, статус;
- `EVIDENCE`: точный первоисточник (URL/документ, редакция, раздел/страница), извлечение, источник утверждения;
- `OUTPUT`: отчёт или артефакт с адресом и хешем, не тождественен факту правильности;
- `AUDIT`: независимая проверка с выводами PASS / REWORK / BLOCKED.
В любом отчёте различать: ПОДТВЕРЖДЕНО первичным источником; ВЫВЕДЕНО (обоснованный вывод); ГИПОТЕЗА; НЕИЗВЕСТНО. Недоказанное не становится фактом после нескольких пересказов агентами.

Постоянная роль и досье отделены от чата. Чаты и runtime заменяемы; задания, решения, версия знания и история должны восстанавливаться вне них. Память модели/граф — поисковый индекс и подсказка, но не единственный источник истины. Реестр источников с SHA/ревизиями неизменяем.

## 6. Правила системной архитектуры (из System Design Primer и проверки действующего PR)
- **Один владелец состояния** задачи; атомарный захват/блокировка, порядок обработки и история изменений.
- **Идемпотентность** по jobId и содержательному SHA: повтор сети не вызывает повторного действия.
- **Не путать подтверждение транспорта с качеством результата.** Сначала получение, затем открытие источника, независимая проверка, только потом переход этапа.
- **Ошибки без молчаливых успехов.** Состояния BLOCKED, NEEDS_AUDIT, WAIT_APPROVAL, EXPIRED; неопределённую отправку не воспроизводить вслепую.
- **Контроль прав:** исполнитель не утверждает собственную работу, аудитор не зависит от директора проверяемого отдела, приоритеты и архитектурные решения утверждает человек.
- **Трассируемость:** цель -> решение -> задача -> источник -> артефакт -> аудит -> сводка. Запись должна быть восстановима после остановки исполнителя.
- **Конфликт версий:** фиксировать родительскую редакцию и SHA, не принимать устаревший доклад вместо свежего.
- **Бюджеты и лимиты:** число запусков, стоимость модели/ключа, частота API, объём хранилища и лимит токенов. Нет автоматического повышения бюджета.
- **Готовность 24/7:** для непрерывной автономности нужны работающий исполнитель и доступные модель/API/учётные данные; Google Drive/GitHub — хранилища, не вычислительная площадка. При выключенной Windows локальный Opera/Archicad не исполняется. Облачное управление возможно отдельно, локальные BIM-операции — только при доступном локальном агенте.

## 7. Учебное задание бюро (без дипломных исследований)
Директор получает одну стратегическую цель: «Найти, изучить и сравнить готовые способы надёжного хранения задач, фактов, связей и аудита для автономного бюро; предъявить источники, ограничения и проверяемый выбор без разработки нового движка».
Исследователь собирает 5-7 первичных ссылок и делает каталог.
Аналитик отмечает лицензии, ресурсы, интерфейсы и зависимости.
Директор проверяет полноту и сопоставляет альтернативы.
Аудитор получает исходные материалы независимо и намеренно проверяет 1 заведомо подставленный неверный факт и 1 устаревшую спецификацию.
Секретариат собирает реестр доказательств; ГАП докладывает руководителю на русском одной сводкой: что сделано, что доказано, что заблокировано, решение и следующий шаг.
Руководитель не маршрутизирует задания вручную и не исправляет текст исполнителей.

## 8. Приёмочные проверки
| ID | Испытание | Условие PASS |
|---|---|---|
| T01 | Постановка цели только ГАП | Директор и исполнитель получают свои задания автоматически, есть маршрут и ID |
| T02 | Каскад делегирования | Каждая роль знает полномочия; исполнитель не обращается к руководителю за рутиной |
| T03 | Первичные источники | 100% существенных фактов имеют проверяемый источник/редакцию; неподтверждённые обозначены |
| T04 | Ложный факт | Аудитор выявляет контрольную ошибку, ГАП не принимает итог до REWORK |
| T05 | Различие транспорт/качество | Квитанция доставки не переводит документ в ACCEPTED без аудита |
| T06 | Повтор события | Один и тот же jobId/receiptSha не приводит к повторному запуску или отправке |
| T07 | Параллельность | Два агента не могут владеть одной задачей одновременно |
| T08 | Сбой после неизвестной отправки | Нет второго сообщения; WAIT_CONFIRM/BLOCKED и отчёт об инциденте |
| T09 | Отказ исполнителя | Задача, артефакты, версии и решения восстанавливаются из устойчивого состояния |
| T10 | Замена чата/агента | Новый исполнитель восстанавливает роль и текущую задачу без пересказа руководителя |
| T11 | Противоречие документов | Обнаружены несовместимые версии; вывод не подменён предположением |
| T12 | Неподчинение незаконному запросу | Неодобренная запись в PLN/main или повышение расходов блокируются |
| T13 | Публикация | Draft PR и квитанция с SHA, ссылки перепроверены, исходники не изменены |
| T14 | Отчёт ГАП | Одна сводка по фактическому состоянию, без заявления о недоказанном PASS |
| T15 | Управление бюджетом | Жёсткое ограничение расходов / токенов и запрет самовольного увеличения |
| T16 | Восстановление | Остановка и повторный запуск не теряют задачи, не дублируют побочные эффекты |
| T17 | Границы производительности | Измерены задержка, процент блокировок, стоимость одного принятого отчёта |
| T18 | Подключение APA (read-only) | Изучается граф/контракт без второй реализации SceneWriter и без изменения PLN |

**Обязательный выпускной критерий:** все критические T01—T16 и T18 проходят в реальной интеграции (не только с имитацией); T17 измерен и признан приемлемым руководителем. Минимум три последовательных завершённых сквозных прогона, один с искусственным отказом, плюс независимая приёмка. Успех офлайн-макета не равен успеху LIVE.

## 9. Рабочие этапы, без самовольного расширения
- G0: зарегистрировать репозитории, точные ссылки, лицензии, версии, стоимость, интерфейсы, угрозы; убедиться, что доступные существующие возможности не переписываются.
- G1: зафиксировать сущности/контракты и изолировать тестовую организацию, учётные данные, очереди и пространство хранения.
- G2: испытать основной управляющий цикл сначала на одном директоре и одном исполнителе; затем расширить роли.
- G3: присоединить информационный контур и сравнить RAGFlow с Dify на одинаковых документах. В активной конфигурации выбрать одну платформу.
- G4: присоединить Graphify, read-only REA/Joern и Spec Kit; сравнить правила ECC и Superpowers, выбрать одну.
- G5: проверить автоматизацию и восстановление; n8n не может стать вторым источником истины для задач.
- G6: прогнать T01—T18; получить независимый аудит и доказательные квитанции.
- G7: выбрать базовую систему и утвердить миграцию существующего координатора; тематические чаты переносить после успешного восстановления. Никаких переделок первой редакции и изменения main без отдельного разрешения.

## 10. Действующие остановочные условия
Запрет на LIVE, если не определены единый писатель, права, бюджет, источник истины, резервное копирование и независимая проверка.
Не разрешать недоказанное автоматическое редактирование нормативов, реальных документов и Archicad PLN.
Не ставить полный ECC и Superpowers одновременно; не ставить RAGFlow и Dify одновременно в одну активную базу.
Перед установкой REA посмотреть точные изменения конфигурации; при исследовании закрытого ПО учитывать законные права на анализ.
Все исследовательские изменения публиковать в feature-ветках и draft PR с SHA; main и действующие чаты сохранять.
