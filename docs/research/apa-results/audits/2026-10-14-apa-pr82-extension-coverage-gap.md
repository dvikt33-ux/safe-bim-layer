# Независимый аудит PR #82: покрытие расширений и API APA — 2026-10-14

**Статус:** AUDITED_FROM_PUBLISHED_SOURCES / INTEGRATION_PARTIAL. Это аудит опубликованного результата, не новый live-тест Archicad и не разрешение записи в PLN.

**Исходное требование:** подключить **все реально доступные программные функции уже установленных расширений и дополнений** к одному существующему APA SceneWriter/SQLite-журналу; в первую очередь переиспользовать готовые программные интерфейсы, а не писать заново их функции. Проверка и совершенствование алгоритмов — после массовой интеграции. Нельзя приравнивать наличие APX к программной доступности его функций.

## Главная недостача относительно задания

PR #82 **не завершает интеграцию всех расширений**. Он покрывает динамическим маршрутизатором Tapir + официальный API, но не доказывает подключение отдельных возможностей других 32 загруженных APX. У некоторых модулей нет известного публичного JSON namespace; автоматического перечислителя всех нативных команд всех APX тоже нет. Для каждого модуля необходимо установить *конкретный способ вызова*, а при его отсутствии — документированное ограничение. Нельзя искусственно обещать 700–1000 команд: источник такого числа не подтверждён, нужно различать команды Tapir, функции C++ DevKit, вызовы внешнего MCP и пользовательские операции UI.

Реестр `schemas/accelerator/capability-registry.json` (snapshot 2026-10-09) содержит **16 разнородных провайдеров**: Tapir, Native Model Dump, SceneWriter, alesdev88, lgradisar, HuskyBIM, MEP, IFC, GDL, Favorites, Hotlink, BibimAI и др. **Это не 16 интегрированных APX.** Категории включают установленные, не установленные, исходные коды, исследовательские данные и SDK-возможности. Их нельзя смешивать с 33 загруженными APX из live-инвентаря. SomeStuff (отдельный исследовательский трек) и внешние Python/MCP-инструменты также не покрываются утверждением «просканировали загруженные APX».

## Требование к следующему этапу: полный capability-ledger

Составить объединённый, устраняющий дубликаты реестр **всего реально присутствующего и относящегося к APA программного стека**:

1. Загруженные и установленные (но не загруженные) APX, официальные компоненты Graphisoft, Tapir и BibimAI, SomeStuff, MEP/IFC/документация; учитывать версии, GUID/идентичности, SHA и наличие правомерного интерфейса.
2. Установленные Python/MCP/CLI адаптеры (в частности alesdev88), собственные источники C++ SDK, IFC-библиотеки и доступные файловые форматы.
3. Для *каждой конкретной функции* фиксировать: `provider`, `operation`, `contract/version`, `read|write|interactive`, `invoke_route`, `runtime_present`, `schema_status`, `execute_status`, `readback_evidence`, `blocker`, `fallback`, `priority`.
4. Статусы разделить: `INVENTORIED`, `CONTRACT_FOUND`, `ROUTABLE`, `LIVE_VERIFIED`, `UI_ONLY`, `BLOCKED`, `NOT_INSTALLED`. Не считать `ROUTABLE` равным `LIVE_VERIFIED`.
5. Если отдельный APX не предоставляет API: проверить документированные штатные Archicad/DevKit-эквиваленты, известный namespace/исходники, безопасный файловый/API-мост; не внедрять слепую автоматизацию GUI и не объявлять «подключено».
6. Подключить найденные **поддерживаемые** маршруты массово через существующий роутер, *без Python-обработчика на каждую команду*, **без второго SceneWriter** и без обхода политики прав/UNKNOWN_OUTCOME.
7. Пройти короткую live-приёмку **по каждому типу транспортного контракта и ключевому классу операций**, включая фактический вызов, сохранение, повторное открытие и независимое чтение; не делать сотни повторяющихся offline-тестов вместо подключения. Для дорогостоящих/опасных вызовов отметить BLOCKED с конкретной причиной.
8. Консолидировать результаты в одну ветку/PR с таблицей `expected / discovered / routable / live / blocked / excluded`, и доказательствами для каждого принятого PASS. Историю испытанного и восстановленного APX не смешивать. Не изменять `main`, действующие PR-heads, рабочие PLN/APX или другие параллельные ветки без отдельного разрешения.

**Acceptance:** законченной полной интеграцией считается не произвольное число 700–1000, а **100% найденных документированных вызываемых интерфейсов установленных подходящих провайдеров классифицированы, подключены через существующую архитектуру либо обоснованно заблокированы**. Для каждого статуса обязательна доказательная ссылка. Нельзя скрыть `NOT_EXPOSED` или засчитать интерфейс GUI как программную команду.
