## Major engineering finding: native multi-neig edit vs singleton Tapir

Official Graphisoft documentation: ACAPI_Element_Edit accepts GS::Array<API_Neig>, transforms a set. Tapir MoveElements currently calls it once per input item with a one-element array. For N identical assembly members and K placements, the Tapir path requires approximately N*K native edits; a properly implemented multi-neig transform could in principle use K calls if a common transform is valid. This is SDK **call-count** analysis, not speed measurement. Crucially, APA already has CloneNativeGroupV1: inspect its C++ implementation before writing anything. It might already exploit multi-neig editing. Group membership, copied GUIDs, children, locked elements and undo semantics need native verification. Current Graphisoft API pages are labelled AC30; AC29 header exactness NOT_VERIFIED.
