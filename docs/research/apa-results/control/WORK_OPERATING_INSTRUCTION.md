## 10. Правила постоянной работы в одном Work-чате

Это постоянная рабочая сессия проекта APA.

При каждом новом цикле:

1. Читать актуальный `PROJECT_PLAN.json` и последние результаты GitHub.
2. Определять ближайшую доступную задачу по обновлённым приоритетам CORE FIRST и зависимостям.
3. Резервировать задачу штатным механизмом `IN_PROGRESS`, owner, lease, claim_ref и проверкой CAS/readback.
4. Выполнять реальную разработку, а не исследования ради исследований.
5. Запускать только необходимые тесты на изменённую функциональность и обязательный CI.
6. Публиковать код, отчёты, доказательства, PR и результаты в GitHub.
7. После readback устанавливать `DONE_PUBLISHED` либо `PARTIAL/BLOCKED` с точной причиной.
8. Самостоятельно переходить к следующей допустимой задаче.
9. При обнаружении полезного инструмента регистрировать его как кандидата и подзадачу соответствующего этапа, не бросая текущую работу.
10. Сохранять контекст в GitHub, чтобы восстановление работы не зависело от длины переписки Work.

**Не останавливать разработку после каждого завершённого шага и не требовать команды «го».** Продолжать выполнение, пока доступен рабочий контекст и разрешённые инструменты.

Если сеанс Work завершился, новый запуск должен продолжаться по GitHub-реестру с последней подтверждённой задачи, а не начинаться с нуля. Не обещать фоновое или непрерывное выполнение вне реально доступного режима Work.

### Запреты

- Не запускать Deep Research без отдельного разрешения.
- Не создавать новые исполнительные архитектуры без реальной необходимости.
- Не повторять успешные 25-/45-элементные тесты без найденной регрессии.
- Не проводить десятки тестов, если один целевой тест и CI дают достаточное доказательство.
- Не изменять main/master и защищённые ветки без разрешения.
- Не выполнять изменения пользовательских PLN/APX без отдельного согласования конкретного воздействия.
- Не считать опубликованный отчёт доказательством успешного native-теста.
- Не тратить время на инфраструктуру, если она не блокирует основной продукт.
- Не заменять работу описанием того, как её можно выполнить.

### Когда обращаться к пользователю

Только если необходимо:
- разрешение на изменение конкретного PLN/APX;
- доступ к отсутствующей системе или учётной записи;
- принципиальное архитектурное решение, которое нельзя принять по текущему плану;
- устранение внешней блокировки, недоступной из Work.

Если Work не имеет доступа к локальному Archicad, выполнить всю возможную GitHub-работу и запросить **одну минимальную локальную операцию**, а не серию повторяющихся команд.

### Формат каждого отчёта

**Задача:** P/A/S ID  
**Подзадача:** конкретное действие  
**Выполнено:** код, PR, CI, native-доказательство  
**Осталось:** точный блокер или следующая задача

Отдельно различать `SOURCE_VERIFIED`, `OFFLINE_PASS`, `LIVE_PASS`, `DONE_PUBLISHED`.
