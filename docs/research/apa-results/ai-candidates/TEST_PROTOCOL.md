# APA — воспроизводимый протокол сравнительных испытаний ИИ (v1)

**Статус:** `PLANNED / NOT_EXECUTED`. Этот документ **не подтверждает** скорость, качество или интеграцию какой-либо модели.

## 0. Запреты и подготовка

- Только локальная **копия** тестовых данных APA; не писать в исходный PLN. Рабочую модель и APX не трогать, пока нет отдельного разрешения.
- Не запускать одновременно новых агентов-писателей в одном репозитории. Во время аудита — read-only права и отдельный Git worktree / ветка.
- Для моделей с внешними запросами — исключить приватные исходники и материалы без разрешения на передачу.
- Скачать только из подтверждённых upstream-источников; указать URL, commit/revision, SHA256 файлов, лицензию и способ установки. Никакого автоматического выполнения сомнительных установщиков/скриптов.
- Если требуется студенческий тариф, платная подписка или расширение RAM, кандидат не проходит входной барьер `FREE_AND_FEASIBLE`.

## 1. Одинаковое оборудование и исходные настройки

Windows 11; Lenovo Legion Pro 5; Ryzen 9 7945HX; RTX 4060 Laptop **8 ГБ VRAM**; **48 ГБ физической RAM**; Archicad 29. Параметры модели (checkpoint, квант, runtime, GPU-layer/offload, thread count, context size, temperature, seed) сохранять для каждой серии. Не сравнивать замеры разных GPU как результат нашего A/B.

Запустить 2 серии: (A) без Archicad; (B) с открытым Archicad 29 и тестовой моделью, без записи. Перед запуском зафиксировать **свободные** RAM и VRAM, после запуска — **потреблённые** RAM/VRAM (пик) и сколько физической RAM остаётся для Windows и Archicad. Отдельно учитывать pagefile и memory mapped weights. Если возникает paging/OOM, немедленно прервать и записать `BLOCKED`.

## 2. Тестовые задачи APA, одинаковые для всех кандидатов

1. **API-grounding:** по выдержке из конкретной версии Archicad API / Tapir схемы определить допустимые поля. Ожидаемое поведение: не изобретать отсутствующие.
2. **C++ code review:** на подготовленных ошибках проверить регистрацию команд, создание элементов, GUID, владение памятью и обработку ошибок; эталон — заранее подтверждённые дефекты.
3. **Python contract & JSON:** построить допустимые read-only запросы; проверить schema, типы, обязательные поля и отказ на невалидных данных.
4. **Geometry consistency:** сопоставить план, этажи, окна и стены по одной системе координат; вычислить расхождения и обозначить неопределённость; эталон — машиночитаемые fixtures.
5. **BIM readback:** на **уже сохранённых** эталонных снимках сравнить ожидание и факт; запрет выдавать `PASS` при отсутствии native read-back.
6. **Adversarial uncertainty:** дать неполную схему API, устаревший источник, противоречивую документацию и заведомо неподтверждённый claim. Успех — явный `NOT_VERIFIED`, запрос источника, а не уверенная выдумка.
7. **Workflow / tool calls:** функция чтения метаданных и поиск документа; подделать ошибку инструмента. Проверить корректную обработку сбоя и **отсутствие записи**.
8. **Architectural layouts (optional):** из структурированного ТЗ вывести набор помещений, связей и ограничений в JSON; Shapely / CP-SAT отдельно проверяют контуры. Никакой AI-картинки как заменителя BIM.

Каждая задача: номер/версия, фиксированные входные данные, ожидаемый результат и независимая проверка. После замены эталона — новая версия бенчмарка.

## 3. Метрики

- **Правильность:** количество корректно выполненных задач / общее число; отдельно серьёзные ложные утверждения и пропущенные дефекты.
- **Надёжность:** доля валидных JSON/tool calls, повторяемость на 3 запусках, соблюдение read-only.
- **Скорость:** TTFT (мс), prompt prefill (tok/s), decode (tok/s), wall-clock на задачу (с), число задач/час. **Не путать TTFT и tok/s**.
- **Память:** вес GGUF на диске, пиковая VRAM, пиковая RAM, фактически доступная RAM после запуска Archicad.
- **Стоимость:** 0 ₽ на постоянно воспроизводимый сценарий; разовые бесплатные кредиты не проходят.
- **Интеграция:** способ вызова, доступность локального API, поддержка Windows, условия лицензии, возможность изолированного запуска.

## 4. Доказательства и публикация

Для каждого реального прогона создать новый файл `runs/YYYY-MM-DD/<model-id>-<run-id>.md` с таблицей тестов, режимами RAM/VRAM, версиями, ссылками на исходники, эталонами, логами, hash, commit и результатом независимой сверки. Обязательно указать `PASS / FAIL / PARTIAL / BLOCKED / NOT_VERIFIED` по каждому пункту. Выполнять GitHub readback после публикации.

Допустимый переход статуса кандидата: `NOT_TESTED → TESTED` **только если опубликованы воспроизводимые данные на оборудовании пользователя**. Не присваивать преимущества модели по числу параметров, маркетинговым бенчмаркам или чужому компьютеру.

Итоговые решения после тестов: `ADOPT` / `RETEST` / `REJECT`; категория из четырёх приоритетов пересматривается отдельно с мотивировкой и датой. Если предлагается внедрение в код APA, подать отдельное предложение через существующий контроль задач и независимый аудит (не редактировать PROJECT_PLAN автоматически).
