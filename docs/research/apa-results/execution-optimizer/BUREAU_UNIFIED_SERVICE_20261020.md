# Единая непрерывная система проектного бюро

Дата: 20.10.2026. Источник: draft PR #187, безопасная ветка; main APA и PLN не изменяются.

## Архитектура

GitHub safe-bim-bridge (jobs, tasks, results) -> один постоянно работающий локальный исполнитель -> SQLite WAL с записью всех переходов -> одна Opera/Automa -> существующие чаты ChatGPT -> документы и квитанции -> следующий адресат.

В тот же процесс загружается существующий source-pinned модуль автономного исполнителя APA из PR #139. Программа удерживает его оригинальную межпроцессную блокировку, не позволяя старому worker работать одновременно. Если прежний worker занят, новый сервис отказывается стартовать. Никаких новых реализаций BIM SceneWriter и команд изменения PLN не создаётся.

GitHub-транспорт использует частый опрос (настраиваемый интервал от 5 секунд), а не настоящий WebSocket или push. Задания обрабатываются по факту регистрации события, без 20-минутной задержки по тактам. Локальная обработка возможна только при запущенной Windows, доступном интернет-соединении, Opera и ChatGPT. При выключенном компьютере или выходе из учётной записи исследование не продолжается.

## Подразделения

Зарегистрированы 19 локальных адресатов: восемь сотрудников Д-01—Д-08, восемь директоров ДИР-01—ДИР-08, секретариат, штаб и управляющий чат APA.

ASSIGN_TASK -> сотрудник -> REPORT_READY -> соответствующий директор -> DEPARTMENT_REPORT_READY -> секретариат -> HQ_BRIEF_READY -> штаб.

Каждый этап требует машинной квитанции о публикации. Переход от сотрудника к директору не означает независимой приёмки: директор получает поручение проверить результат. В штабе остаются полномочия по архитектурным решениям. ARENA_RESULT_READY доставляется управляющему чату APA. Отдельный исходный ограниченный APA-приёмник в том же процессе продолжает безопасные native READ_ONLY jobs.

## Очередь и отказы

QUEUED -> LAUNCHING -> WAIT_TAB -> WAIT_SUBMIT -> WAIT_RESULT -> COMPLETE_REPORTED.

Активация без отправки: WAIT_TAB -> COMPLETE_ACTIVATION.

До подтверждённого выбора вкладки нельзя заявлять запуск нужного чата. После подтверждённой отправки сообщение переводится в WAIT_RESULT; это состояние занимает соответствующий чат, но освобождает интерфейс Opera для другого чата. Повторная отправка после неопределённой ошибки запрещена.

Неизвестный результат во время управления интерфейсом -> BLOCKED_UI (останавливает новые операции Opera до проверки). Сбой отдельного исследования -> BLOCKED_CHAT (другие чаты остаются работоспособными). Истёкший срок QUEUED -> EXPIRED. Некорректные события изолируются в таблице rejected и не блокируют остальные. У каждого задания неизменный jobId и сверенный SHA Git blob. Токен подтверждения создаётся случайно и сохраняется только локально.

Состояния и журнал хранятся в SQLite (synchronous FULL). Межпроцессная блокировка не допускает второго экземпляра бюро. Повтор сетевого ACK обрабатывается без дублирования поручения.

      "targetChat": "D-03",

    {
      "schema": "BUREAU_TASK_V1",
      "jobId": "d03-task-20261020",

Квитанция results/<jobId>.json:

    {
      "schema": "BUREAU_RECEIPT_V1",
      "jobId": "d03-task-20261020",
      "status": "REPORT_PUBLISHED",
      "documentUrl": "https://docs.google.com/document/d/ИДЕНТИФИКАТОР/edit",
      "summary": "Материал зарегистрирован и ожидает проверки директора"
    }

При завершении проверяется существование квитанции в GitHub и её SHA. URL документа сам по себе не означает проверенного качества или наличия доступа к документу; задача следующего адресата — независимая проверка.

## Единый Automa workflow

Один Automa workflow (v1.28.26+) может обслуживать все адресаты. Локальный JSON содержит workflowId (везде одинаковый при желании) и точный chatUrl для каждой существующей вкладки. Адреса чатов не отправляются на GitHub.

При запуске расширение получает параметры jobId, token, callbackPort. Рабочий процесс:

1. HTTP GET http://127.0.0.1:<callbackPort>/task?jobId=<jobId>&token=<token>. В ответ: targetChat, chatUrl, action, instruction.
2. Switch Tab выбирает существующую вкладку по точному chatUrl и сверяет её URL. Новую вкладку ChatGPT не создавать.
3. После реального выбора: POST http://127.0.0.1:<callbackPort>/ack с полями jobId, token, stage=TAB_SELECTED, proof.
4. Если action=DELIVER_TASK: вставить instruction, проверить поле ввода, однократно отправить. После фактической отправки: POST со stage=MESSAGE_SUBMITTED.
5. Когда готов и опубликован результат, отдельный POST stage=RESULT_PUBLISHED включает receiptSha существующего GitHub-файла; без него следующий отдел не запускается.
6. В случае ошибки stage=FAILED. Запрещено автоматически повторять неопределённую отправку.

URL-активация подтверждена в официальной документации Automa:
https://www.goautoma.com/extension/docs/blocks/trigger.html
Фоновое HTTP-взаимодействие описано:
https://www.goautoma.com/extension/docs/blocks/javascript-code.html

**Сборка этого рабочего процесса и его работа в реальной Opera пока не прошли сквозной LIVE-тест.**

## Один раз установить на пользовательской Windows

1. Получить ветку PR #187 локально, не заменяя стабильную папку APA.
2. Скопировать examples/bureau-unified-config.example.json в C:\LocalAI\BureauUnified\config.json. Заполнить настоящий общий workflowId и chatUrl существующих чатов. Проверить путь operaExe, ID установленного Automa и реальный путь к установленному worker PR #139.
3. Убедиться, что прежний PR #139 worker завершил задание; остановить только его фоновый процесс, не закрывая текущие ChatGPT-чаты. Установщик не завершает старый worker насильственно.
4. Выполнить из ветки PR #187:

    python scripts/install_bureau_unified_service.py --config C:\LocalAI\BureauUnified\config.json

Установщик проверяет точный SHA исходного Git blob старого worker, фиксирует его локальную контрольную сумму, копирует новые файлы в отдельную папку, отключает старый автозапуск только во время безопасного перехода, запускает единый процесс, проверяет localhost /health и создаёт install-receipt.json. При ошибке восстанавливает старый Startup-файл. Установщик не меняет главный APA, Archicad, PLN, Arena и стабильные рабочие файлы.

Квитанция BUREAU_UNIFIED_LOCAL_PROCESS_READY при apaAttached=true подтверждает лишь процесс и оригинальный модуль APA. Она не доказывает отправку сообщений через Automa и публикацию отчётов.

**Автоматическое восстановление:** новый Startup VBS ожидает завершения единого процесса; после аварийного завершения снова запускает его. SQLite-журнал сохраняет незавершённые задания, которые с неопределённым исходом не переисполняются. Для плановой остановки сторожевого автозапуска создать файл C:\\LocalAI\\APA_AC29_Stable\\bureau-unified-state\\PAUSE_AUTOSTART и завершить выполняющийся процесс после сохранения его статуса. Для возобновления удалить файл и заново запустить новую запись Startup либо войти в учётную запись Windows. Это ещё не заменяет реальный Windows LIVE-тест восстановления.

## Приёмочные стадии

1. Офлайн CI: только новые тесты и исходники.
2. Локальная установка: LIVE_READY по квитанции установки.
3. TRIGGER_PROBE: GitHub -> Automa -> выбор существующего Д-03 -> COMPLETE_ACTIVATION без отправки.
4. DELIVER_TASK: проверенное однократное сообщение Д-03 -> WAIT_RESULT.
5. Реальная опубликованная квитанция -> директор -> секретариат -> штаб; без имитации ответов.
6. Перезапуск Windows/Opera, сохранность очереди, отсутствие повторного сообщения.
7. После этого — независимый push/WebSocket-транспорт при необходимости.

До завершения пунктов 2—6 нельзя называть систему непрерывно работающей на компьютере пользователя.
