# Глобальный ШТАБ GPT — дорожная карта интеграции и реестр технических решений

**Редакция:** V0.3.3 · **Дата фиксации:** 29.10.2026  
**Статус:** проект плана для утверждения; не означает, что приведённые интеграции уже внедрены.  
**Предмет:** планировщик, диспетчеризация, организационная структура, общая память результатов, контроль публикаций и мобильный монитор. Это не техническое задание на переработку APA, МОАГ или Archicad.

## I. Цель и обязательные правила

Владелец взаимодействует преимущественно с главами организаций. Те самостоятельно организуют задачи, выбирают существующие рабочие места или создают новых исполнителей в пределах разрешённых бюджетов. Каждый проект изолирован по управлению и данным; разрешённые, снабжённые источниками знания могут использоваться другими проектами. Система масштабируется через рекурсивные организационные узлы. iPhone используется как постоянно открытый монитор; ноутбук остаётся рабочей станцией. Облако обслуживает сохранённое состояние и монитор, а Windows/Opera/Archicad выполняют только свои локальные операции.

**Базовая модель исполнения (обязательная):** действующие и новые **обычные чаты ChatGPT** — основные интеллектуальные исполнители; чат руководителя — обычный ChatGPT-чат. Постоянны рабочее место и досье; отдельный чат может заменяться. Codex используется при BUILD, но не как штатный исполнитель RUN. Внешние агентные runtime и API-модели не заменяют штатные чаты без отдельного решения пользователя. 

**Правило повторного использования:** сначала внутренние существующие результаты; затем готовые внешние платформы; собственная разработка — только для выявленного функционального пробела. **Правило интеграции:** один действующий управляющий контур, один владелец состояния каждого задания, одна проверенная интеграционная база, одна активная стадия с записью результатов. **Правило приёмки:** исходники/ссылки + версии/SHA + CI + нужный LIVE + обратное чтение публикации + проверка несовместимостей. Не путать наличие кода, успешный CI и работающую систему.

## IV. Исследовательские карточки «на карандаше»

Не запускать новые исследования без проверки «есть ли уже решение». Каждая карточка ограничена конкретным выбором и обязательным финальным исходом.

- **K1. Реальные обычные чаты ChatGPT — первоочередная проверка.** Как существующий чат главы получает поручение, публикует итог и уведомляет планировщик через доступные официальные приложения/встроенные инструменты? Как исключить повторное введение и обеспечить перенос роли при переполнении чата? PR #187 — исходный код для оценки, Paperclip — лишь возможный управляющий уровень, не конкурирующий runtime исполнителей.
- **K2. Fibery/Paperclip/собственная PWA.** Выбрать минимальный мобильный монитор с живыми статусами, стоимостью, правами и возможностью обновления без ноутбука. Итог: одна пользовательская панель, никаких двух независимых реестров.
- **K3. Законный и технически поддерживаемый выпуск результатов обычных чатов.** Отдельно исследовать встроенные ChatGPT Projects, приложения, Tasks и пользовательские процедуры публикации. Пользовательское разрешение не отменяет условия OpenAI: запрещено автоматически/программно извлекать Output из потребительского сервиса. Не использовать скрейпинг DOM или недокументированные методы как штатный контур. Этап может быть BLOCKED до появления разрешённого интерфейса; iOS проверяется отдельно.
- **K4. События и надёжность.** Измерить возможности PR #187 и только при проблеме сравнить n8n/Inngest. Итог: точно один механизм исполнения побочных эффектов с идемпотентными квитанциями.
- **K5. Документный поиск.** Проверить PR #69/#71 на нормативных документах и межпроектных запросах; только при доказанной недостаточности сравнить RAGFlow/Dify. Итог: выбор на основе источниковой точности и затрат.
- **K6. Доступ к внешним сервисам и модельным ресурсам.** Проверить, что доступные модели и тарифы/лицензии покрывают тестовые роли; автономный «найм» не должен предполагать безлимитные API или свободный доступ к существующим разговорам.

## V. Дисциплина разработки: против потери веток

1. **Единый реестр:** карточка каждого компонента с URL, веткой, commit SHA, владельцем, лицензией, входным и выходным контрактом, тестами, запретами, зависимостями и статусом.
2. **Одна активная стадия интеграции:** будущие идеи попадают в «на карандаше» и не захватывают общий управляющий контур.
3. **Один владелец данных:** не позволять Paperclip, PR #187 и n8n одновременно считать себя главной очередью одних и тех же заданий.
4. **Блокирующие проверки перед слиянием:** контракт → тесты → необходимый LIVE → readback → аудит → фиксация интеграционной версии. Готовность кода не равна интеграции.
5. **Нет слепых повторов:** если публикация/отправка дала неопределённый ответ, сначала проверить удалённый результат по идентификатору/SHA; не создавать дубль.
6. **История решений:** сохранять причины выбора, отвергнутые варианты, изменения версий и `superseded_by`; карточки незавершённых компонентов не удалять.
7. **Безопасность:** не класть секреты, URL приватных чатов и персональные данные в публичный GitHub; тестовые исполнители не пишут в действующий Archicad/PLN/main без отдельного допуска.
8. **Не требовать от постоянного чата существования вечно:** роль и память — долговечные сущности, конкретные чат и модель могут быть заменены.

## VI. Первые решения для Э0

- Не писать новый код и не устанавливать сразу все внешние платформы.
- Утвердить место хранения реестра и точную интеграционную базу (main действующих систем без разрешения не менять).
- По исходникам проверить PR #187 и #193, а также официальные возможности **обычных** ChatGPT-чатов. Paperclip проверять только как вспомогательный control plane, без подмены чатов другими агентами.
- Провести безопасный изолированный тест с обычными ChatGPT-чатами и документированной публикацией; сравнение Paperclip — вторым шагом, только если требуется дополнительное управление. Не автоматизировать извлечение Output вопреки условиям OpenAI.
- Зафиксировать один источник состояния TASK и способ работы именно с обычными чатами; только после этого дополнять межчатовую доставку.

## IX. Контрольный эксперимент Э1 (ещё не выполнен)

Тестовые контуры строго изолированы и имеют разные БД, учётные данные и очереди:

- **A:** PR #187 — локальный исполнитель и SQLite, без боевых адресатов.
- **B:** Paperclip — отдельная тестовая организация с синтетическими задачами, без доступа к пользовательским чатам и APA writer.
- **C (опционально, только после A/B):** Paperclip как единственный MASTER TASK + PR #187 как делегированный транспорт DELIVER_TASK с квитанциями; никаких самостоятельных переводов master-статуса PR #187.

### Открытые вопросы, специально не скрывать

- Автоматическое получение сообщений/ответов из обычных чатов ChatGPT (iOS и десктоп) **не доказано**; официальные условия потребительского ChatGPT запрещают автоматическое/программное извлечение Output. Нельзя объявить PR #187 полностью пригодным для такой схемы без проверки допустимости и поддерживаемых интерфейсов. Источник: https://openai.com/policies/terms-of-use/ .
- Универсальная многоуровневая структура «глобальный штаб → несколько компаний → подразделения» в Paperclip требует проверить различие между оргдеревом внутри компании и самой верхней границей company: одно не доказывает другое.
- Доступная модель и бюджет не означают, что бесплатно доступны тысячи автономных запусков.
- Мобильный браузерный интерфейс не гарантирует удержание экрана активным, push-уведомления или обновление в фоне на iPhone.
- Приватные чат-ссылки, секреты и личные файлы запрещены в публичном GitHub; репозиторий может содержать лишь обезличенную архитектуру и адреса публичных исходников.

## XII. Политика ресурсов: Codex при разработке разрешён, при эксплуатации запрещён (уточнено 29.10.2026)

**Решение пользователя:** лимит Codex МОЖНО и при необходимости НУЖНО использовать для проектирования, написания и изменения кода, интеграции готовых компонентов, тестирования и развёртывания глобального ШТАБа. Расход на разработку допускается. **После запуска штатная работа ШТАБа не должна расходовать лимит Codex.** Не распространять прежний запрет на создание системы.

### Разделяем два контура

1. **BUILD / разработка:** ChatGPT, Codex CLI/Cloud или иные инструменты разработки могут выполнять разовые задачи проектирования, исправления и проверки кода; результат фиксируется в GitHub и проходит приёмку. Codex может использоваться повторно для отдельных обновлений по решению пользователя.
2. **RUN / эксплуатация:** планировщик, его руководители, сотрудники, фоновые процессы, таймеры, уведомления, отчётность, индексирование и восстановление после ошибок работают без запросов к Codex и без потребления его лимита. Штатные агенты используют только отдельно согласованные не-Codex движки или детерминированные механизмы.

### Технический запрет на неявный расход

- Для производственной конфигурации не включать `codex_local`, Codex Cloud и любые штатные цепочки, которые под капотом вызывают Codex. Codex-адаптер Paperclip изучать/тестировать в BUILD можно; в RUN не разрешать.
- Если выбранный управляющий контур не умеет работать без Codex, он не подходит для RUN до замены runtime.
- Доступ к Codex-учётным данным не выдавать производственным исполнителям. Предусмотреть явный allowlist моделей/провайдеров, отдельные ключи и бюджеты, аудит вызовов, fail-closed для неизвестных адаптеров. Не считать запрет в промпте достаточной защитой.
- Отдельно оценить стоимость не-Codex исполнения: локальные модели, доступные бесплатные квоты или платные API; нулевой расход Codex не равен нулевой общей стоимости.
- Любая будущая автоматическая самопереписка системы с использованием Codex — отдельное, явно санкционированное задание BUILD, не фоновое действие RUN.

### Приёмка

**Тест A (BUILD):** Codex разрабатывает/исправляет компонент, опубликованы PR, версия и тесты — использование лимита допустимо.

**Тест B (RUN):** запускаем систему, несколько организаций выполняют задания, отчёты и восстановление; при этом Codex не вызывается напрямую и через адаптеры. Отсутствие вызовов проверяется по журналам и конфигурации/маршрутам доступа, а не только по словам агента.

**Тест C (ошибка конфигурации):** попытка назначить Codex штатным исполнителем получает отказ до запуска, без расхода лимита.

### История решения

V0.3.1 ошибочно запрещала Codex и на разработку. Это ограничение **отменено и заменено настоящим разделом**. Для Э0–Э7 сохраняются принципы reuse-first, одного управляющего контура, поэтапной приёмки и осторожной работы с существующими чатами.


## XIII. Базовое требование: действующие чаты ChatGPT — штатные сотрудники (уточнение пользователя 29.10.2026)

1. **Кто выполняет интеллектуальную работу:** руководители, директора, специалисты, аудиторы, секретари — обычные беседы ChatGPT, в том числе уже созданные в проектах пользователя. Не подменять их Codex CLI, Paperclip-адаптерами, локальными моделями или оплачиваемыми API без отдельного решения пользователя.
2. **Что делают внешние инструменты:** ведут задания/иерархию, долговечную память, маршрутизацию разрешённых событий и публикаций, мобильный монитор, контроль статусов. Их собственные ИИ-движки в штатном RUN не требуются и не должны автоматически запускаться.
3. **Должность не равна чату:** постоянный ID рабочего места, профиль роли, задания, результаты и история должны существовать вне одного ChatGPT-диалога. Новый чат получает только разрешённый актуальный контекст.
4. **Гарантированная автоматическая передача между обычными чатами пока НЕ ДОКАЗАНА.** Project memory — контекстуальная возможность, а не надёжная межчатовая событийная очередь. Запланированные задачи имеют отдельные ограничения и не дают универсальный push в произвольный существующий чат.
5. **Политика OpenAI и безопасность:** действующие пользовательские Terms of Use (01.01.2026) запрещают автоматически/программно извлекать данные или ответы из сервиса. Проверять только документированные, разрешённые пути (например, публикация результата самим чатом в подключённое хранилище, если доступна и разрешена, или инициируемое пользователем сохранение). Не считать browser DOM scraping допустимой основной архитектурой и не обходить ограничения аккаунта. Источники: https://openai.com/policies/terms-of-use/ ; https://help.openai.com/en/articles/10169521-projects-in-chatgpt ; https://help.openai.com/en/articles/10291617-scheduled-tasks-in-chatgpt .
6. **Главный эксперимент Э1:** существующий ChatGPT-чат A создаёт документированный результат через поддерживаемую функцию → в реестре появляется запись с URL/версией → существующий ChatGPT-чат Б открывает её через разрешённое подключение → глобальный штаб видит факт. Если процесс требует ручного действия, это честно фиксируется как `PARTIAL_MANUAL`, а не автономность.
7. **Взаимодействие с iPhone:** отдельный мобильный монитор показывает записи из согласованного хранилища. Сбор сообщений нативного приложения ChatGPT на iOS не предполагается без разрешённого механизма.
8. **Изменение приоритета:** Paperclip перенесён из предпочтительной платформы исполнителей в кандидаты на административный слой; PR #187 сохраняется как ключевая старая разработка, требующая и технической, и нормативной проверки. Разработка через Codex разрешена; штатная эксплуатация не расходует Codex.
