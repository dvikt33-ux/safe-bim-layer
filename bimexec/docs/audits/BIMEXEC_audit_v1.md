# Независимый технический аудит архитектуры BIMEXEC
### Автоматизированное управление Archicad 29 — переход от dry-run к реальному исполнению

**Дата:** 2026-09-26
**Объект аудита:** BIMEXEC Router (локальный), модель JOB → PACKAGE → OPERATION, mapping BIMEXEC ID → Archicad GUID, read-back verification, dependency engine, recovery.
**Режим аудита:** независимый. Синхронизация с внешними оркестраторами в scope не входит.
**Предпосылка:** Router уже работает, dry-run executor, WriteGate, DuplicateMutationGuard, read-back v1, JSON parser, job state, последовательная очередь, fail-closed recovery, synthetic self-tests — реализованы. Мутирующие вызовы Archicad отключены. Сохранение PLN — вне BIMEXEC.

---

## 0. Метод и границы

Аудит проведён по модели «что сломается при первом же реальном write», с явным допущением, что:

1. **LLM не является доверенным источником** ни на одном этапе после валидации плана. План от ChatGPT — это *ненадёжный вход*, а не программа.
2. **Инструментальный слой (BIBIM / Archicad-MCP / Tapir) не является транзакционным** и не даёт гарантий «применено / не применено» после таймаута.
3. **Archicad — однопользовательское GUI-приложение с общим глобальным состоянием** (выделение, текущий инструмент, комбинация слоёв, активное окно, undo-стек). Любое из этого — разделяемый ресурс, и Router делит его с живым человеком.

Проверенные внешние факты, использованные в аудите:

| # | Факт | Источник |
|---|---|---|
| F1 | Официальный JSON/Python API Archicad **не умеет создавать и редактировать элементы** — для этого нужен Add-On (Tapir/BIBIM). Tapir добавляет «создание и редактирование *некоторых* элементов», манипуляции этажами, перемещение; покрытие частичное и активно меняется. | [2](https://archi-xt.com/posts/archicad-automation-technologies/) |
| F2 | Известен баг AC29: **read-команды Tapir/MCP падают на Pydantic-валидации** (`Extra inputs are not permitted`), при этом **write к тем же элементам проходит**. То есть «писать можно, прочитать — нельзя» — реальный, а не теоретический режим. | [4](https://github.com/ENZYME-APD/tapir-archicad-automation/issues/659) |
| F3 | MCP-слой умеет **обнаруживать несколько запущенных инстансов Archicad** и адресовать команды по порту, управлять ими одновременно. | [5](https://glama.ai/mcp/servers/SzamosiMate/tapir-archicad-MCP) |
| F4 | C++ API даёт настоящую границу транзакции: `ACAPI_CallUndoableCommand`. Модификации вне undo scope **возвращают ошибку**; возврат `APIERR_CANCEL` из лямбды **отменяет все модификации внутри scope**. | [3](https://archicadapi.graphisoft.com/category/tutorial/feed) |
| F5 | В экосистеме есть выделенное разделение read-only / write команд на уровне MCP-инструмента (мутирующие команды отклоняются в read-пути). | [1](https://glama.ai/mcp/servers/alesdev88/Archicad-MCP/tools/execute_read_api_command) |
| F6 | Поле `Element ID` (`General_ElementID`) доступно как встроенное свойство через property API — то есть его можно использовать как машинный маркер для привязки. | [2](https://github.com/SzamosiMate/multiconn_archicad) |

> **Главный вывод аудита (tl;dr).** Предложенная модель Package/Operation — правильный вектор, но она описывает **только happy path**. В ней отсутствуют три сущности, без которых write-режим unsafe:
> 1. **Третье состояние мутации — UNKNOWN** (между «успешно» и «провал»). Текущая логика бинарна.
> 2. **Жизненный цикл mapping ID→GUID** как полноценной сущности с состояниями и provenance. Сейчас mapping — это, по сути, «запомнить то, что вернул инструмент», а инструмент может вернуть чужой GUID, и никто это не поймает.
> 3. **Проверяемость (verifiability) как часть контракта.** Пока `verify_spec` не лежит в задании, Router неизбежно начнёт «угадывать» и подкручивать допуски. А факт F2 означает, что в AC29 вы столкнётесь с ситуацией «write прошёл, прочитать нельзя» буквально на первом прогоне.
>
> Вердикт: **до production-safe v1 доводимо** без транзакций и без компенсаций, но при жёстком сужении области (только `create` + узкий `change`) и при условии реализации P0-чеклиста из раздела F.

## A. Critical blockers

Речь о вещах, при которых первый же реальный write либо повредит модель, либо создаст неотличимую от успеха тихую ошибку.

### A1. Отсутствует состояние UNKNOWN для мутации
Текущая логика бинарна: `ok → next operation`, `mismatch → PAUSED`. Но у мутирующего вызова **три** исхода, не два:

```
применено      → подлежит проверке
не применено   → можно (осторожно) считать провалом
НЕИЗВЕСТНО     → таймаут, обрыв соединения, 5xx, kill процесса, "успех, но модель не изменилась"
```

Третий исход нигде не представлен. Следствия:
- Router не знает, создана ли стена;
- автоматический повтор запрещён (правильно) → задание зависает без диагноза;
- «считать провалом и идти дальше» → дубль в модели при следующем создании.

**Требование:** состояние `OP_DISPATCHED_UNKNOWN` (до выяснения) → job `PAUSED(reason=OP_UNKNOWN)` → **глобальная остановка всех мутаций в job**, пока человек не примет решение. Это состояние обязано быть самым «громким» в системе.

### A2. Idempotency key не существует как сущность
`DuplicateMutationGuard` в текущем виде решает задачу частично и имеет три дыры:
1. **Не переживает рестарт Router** (in-memory) → после падения guard пуст → replay → дубль.
2. **Ключ на основе хэша payload**: (а) два легально одинаковых элемента (симметричные проёмы, типовые стены) могут быть ошибочно схлопнуты; (б) наоборот — ре-сериализация того же задания с другим порядком ключей или форматированием чисел даст **новый** ключ для той же операции → дубль при retry.
3. **Не различает «не отправляли» / «отправили, ответ неизвестен» / «подтверждено»** — а это ровно те три состояния, из которых строится recovery.

**Требование:**
```
idempotency_key = H(job_id, plan_hash, package_id, op_id, attempt_no)
attempt_no = 1  для ВСЕХ мутирующих операций (жёстко, без исключений)
```
Ключ записывается в WAL **до** отправки вызова. Повторная доставка того же задания по HTTP возвращает текущий статус job, а не инициирует новую отправку.

### A3. Mapping привязывается к ответу инструмента, а не к прочитанной модели
Ответ `create_*` с GUID — это **обещание**, а не доказательство. Классические сценарии тихого искажения mapping:
- инструмент вернул GUID **последнего/первого** элемента в текущей выборке, а не созданного;
- инструмент вернул GUID элемента, созданного **предыдущей** операцией (off-by-one при батчевой внутренней реализации);
- ответ пришёл от **другого инстанса Archicad** (см. A5);
- mapping записан до верификации, верификация провалилась, но зависимые пакеты уже читают «подтверждённый» GUID.

Всё это молча направляет последующие операции (проёмы, move, delete) **в чужой объект**.

**Требование:** mapping получает статус `CONFIRMED` **только** по результату read-back, доказавшего соответствие по маркеру или по набору якорей (см. A4, инвариант I8). До этого статус — `CLAIMED`, и **ни одна другая операция не имеет права его читать**.

### A4. Нет механизма однозначной привязки созданного объекта
Вопросы «что делать, если объект существует, но GUID неизвестен» и «как исключить привязку к неправильному объекту» в текущей модели не решены. Поиск «по геометрии» не годится: две стены с одинаковыми координатами — это не редкость после повторного запуска, и это ровно тот случай, который нужно уметь *детектить*, а не разрешать наугад.

**Рекомендация (основной путь): маркерная привязка.**
```
create_element(...)
  → set Element ID = "BX:<job_id>:<op_id>:<nonce>"     # в том же undo scope, если доступно
  → read-back: поиск элемента по маркеру Element ID
  → ровно 1 найден + type/story/layer совпали + геометрия в допуске
  → mapping = CONFIRMED (method = MARKER_MATCH)
  → (опционально) перезаписать Element ID в человекочитаемый BIMEXEC ID
```
Поле `Element ID` доступно как встроенное свойство через property API (F6), так что путь реализуем. Маркер делает объект **уникально находимым** независимо от того, что вернул `create`, и независимо от того, что делал пользователь в промежутке.

**Fallback (если запись ID недоступна через адаптер):**
1. Precondition emptiness: до создания проверить, что в области (этаж + слой + bbox операции) **нет** элементов данного типа. Зафиксировать fingerprint.
2. После создания — anchor-поиск по (type, story, layer, geometry).
3. **Ровно 1 кандидат** → `ADOPTED_BY_ANCHOR`, mapping = `CONFIRMED` с пометкой о методе.
4. **0 кандидатов** → операция не применена (или применена «не там») → `VERIFY_FAILED`.
5. **>1 кандидат** → `PAUSED(AMBIGUOUS_MATCH)`. Ни в коем случае не брать «первый» или «последний созданный».

### A5. Нет привязки job к конкретному инстансу Archicad и проекту
MCP-слой адресует команды **по порту** и умеет работать с несколькими одновременно запущенными инстансами (F3). Сценарии:
- Archicad перезапущен → тот же порт, но это уже другой проект / другое состояние;
- открыт второй Archicad → порт уехал;
- человек открыл другой PLN в том же инстансе.

Без проверки binding мутации уйдут **в чужой проект**, причём read-back тоже уйдёт туда же и, скорее всего, «пройдёт» — ошибка станет необнаружимой.

**Требование:** binding = `(port, projectPath, projectName, isUntitled, isTeamwork, stories_fingerprint, archicad_version, adapter_version)`. Binding перепроверяется **перед каждым мутирующим вызовом** (дешёвый read-only вызов `GetProjectInfo`). Расхождение → `PAUSED(INSTANCE_MISMATCH)`. Re-bind — только через человека.

### A6. Верификация не специфицирована в задании → её невозможно реализовать корректно
В Archicad геометрия элемента **меняется сама** после создания, без участия Router:
- стены **соединяются и обрезаются** в T-стыках и пересечениях → длина 12.0 м прочитается как 11.62 м на корректной модели;
- референсная линия стены (центр / внутренняя / внешняя грань) — `from/to` + `thickness` без явного указания даёт ошибку в половину толщины;
- направление стены (flip) инвертирует локальную систему координат проёмов;
- верх стены может быть привязан к вышележащему этажу → `height` перестаёт быть числом.

Сравнение «как отправили, так и прочитали» даст **ложные mismatch** на абсолютно корректной модели. А естественная реакция на ложные mismatch — «ослабить проверку» → настоящие ошибки начнут проходить. Это ловушка, в которую такая система попадает гарантированно.

**Требование:** per-operation `verify_spec` — декларативный набор проверок с допусками, **инвариантных к ожидаемым стыкам**:
```json
"verify": {
  "checks": ["exists", "type", "story", "layer", "marker", "ref_line", "angle", "midpoint", "length_approx", "count_delta"],
  "tolerance": { "length_m": 0.05, "coord_m": 0.01, "angle_deg": 0.5 },
  "expect_join": true,
  "count_delta": { "Wall": 1 }
}
```
Проверять **референсную линию, угол, середину, длину с допуском на обрезку** — а не точные конечные точки.

### A7. Нет capability gating на этапе валидации: write может быть доступен там, где read-back нет
Это не теоретический риск. В AC29 известна ситуация, когда read-команды Tapir/MCP ломаются на Pydantic-валидации, а **write к тем же элементам проходит** (F2). Официальный JSON/Python API в принципе не создаёт элементы (F1), то есть создание целиком зависит от Tapir/BIBIM, чьё покрытие частично и меняется от сборки к сборке.

Следовательно: **«успешный write + невозможный read-back» — это штатный режим, а не исключение.** Система обязана уметь его распознать и остановиться, а не «продолжить, потому что ошибок не было».

**Требование:** capability matrix (шаблон в Приложении 3) строится до прогона. Любая операция, у которой нет **подтверждённого** пути read-back, — `OUT_OF_SCOPE`, и job **отклоняется на этапе VALIDATE**, а не падает в рантайме на 40-й операции.

### A8. Нет детектора расхождения модели (model drift) и глобального fingerprint
Archicad — это GUI с живым человеком. Между шагами Router пользователь может: подвинуть элемент мышью, нажать Ctrl+Z, переключить этаж, сменить комбинацию слоёв, сменить инструмент, изменить выделение. Любое из этого делает внутреннюю модель Router устаревшей, причём никакая проверка отдельного элемента этого не поймает.

**Требование:** дешёвый модельный fingerprint на PRECHECK и POSTCHECK каждого шага:
```
fingerprint = H( counts_by_type_and_story, stories_list_with_elevations, layer_state_hash, project_info )
```
Правила:
- fingerprint на PRECHECK шага **равен** сохранённому после предыдущего шага → иначе `PAUSED(MODEL_DRIFT)`;
- дельта счётчиков на POSTCHECK **точно равна** ожидаемой (`count_delta`) → иначе `PAUSED(VERIFY_FAILED)`.

`count_delta` — самая дешёвая и самая эффективная проверка в системе: она одна ловит двойное создание, «создалось не там» и кражу GUID.

### A9. `depends_on` на уровне пакета не выражает частичное выполнение
PKG02 создал 8 стен из 12 и встал на VERIFY_MISMATCH. Что означает «PKG04 depends_on PKG02»? В текущей модели — ничего. А это ключевой вопрос: проёмы в 4 несуществующих стенах не должны создаваться.

**Требование:** явные состояния пакета, из которых следует единственное правило v1:

> Зависимость считается удовлетворённой **только** при `package.status == COMPLETED`.
> `PARTIAL` → зависимые пакеты `BLOCKED` → job `PAUSED(DEPENDENCY_BLOCKED)`.
> Никаких «soft deps» и «попробуем дальше» в v1.

### A10. Порядок исполнения не определён: массив или топология?
Если порядок = порядок массива `packages[]`, то `depends_on` — декоративный атрибут, и рассинхронизация между declared-графом и фактическим порядком останется незамеченной навсегда. Если порядок топологический — нужны детектор циклов, проверка существования зависимостей и детерминированный tie-break. Сейчас нет ни того, ни другого.

Отдельно: внутри пакета порядок операций = порядок массива `operations[]`, и это **нормально** (детерминизм важнее планировщика), но должно быть зафиксировано и проверено: любая ссылка на объект (`host_wall`) обязана указывать на операцию **раньше** в этом пакете или в пакете из `depends_on`.

### A11. Единицы, базис и система координат не заданы
Пример задания:
```json
"from": [0, 0], "to": [12, 0], "height": 3.0, "story": 0
```
Ни единиц, ни начала координат, ни datum высот, ни референсной линии, ни уровня низа стены. Это тихий источник ошибок на метры, который не поймает никакая проверка «успешности вызова».

Особенно опасен `"story": 0` как **индекс**:
- индекс меняется при изменении набора этажей;
- индекс 0 — это «первый в списке», а не «первый этаж здания»;
- индекс нестабилен, если пользователь переупорядочил этажи.

**Требование:** этаж резолвится по **имени + отметке** (elevation), в job state хранится `story_uid`/отметка, индекс допустим только как подсказка, проверяемая по отметке. Плюс обязательные поля: `units`, `origin`, `elevation_datum`, `reference_line`, `base_level`, `top_link`.

### A12. Job state не является источником истины, переживающим падение
«Job state» + «последовательная очередь» без write-ahead journal и атомарной записи → после краха Router **не знает, была ли мутация применена**, и recovery превращается в угадывание. Это критично, потому что ровно этот сценарий («kill -9 между dispatch и verify») будет самым частым на реальном прогоне.

**Требование:** append-only journal (fsync **до** отправки мутирующего вызова) + snapshot состояния через atomic rename. Recovery = только reconcile + человеческое решение, никогда — автоматический вывод.

### A13. Нет `plan_hash` и иммутабельности плана
Без хэша плана возможны: смешивание версий плана в одном job (часть от v1, часть от v2), молчаливое «дозаписывание» пакетов в выполняющийся job, недетектируемое расхождение между тем, что человек одобрил, и тем, что исполняется.

**Требование:** `plan_hash = H(каноническая сериализация packages[])`. Хранится в job, проверяется на каждом шаге, иммутабелен. Любое изменение плана = **новый job_id**. Изменение плана «на ходу» запрещено.

## B. High-risk issues

### B1. Нет single-writer лока и process singleton
Сценарии interleaving мутаций в один Archicad:
- dev- и prod-инстанс Router одновременно;
- рестарт при живом старом процессе;
- повторная доставка того же job по HTTP (клиент, прокси, ретрай ChatGPT);
- два job в очереди, один из которых в PAUSED, а второй продолжает писать.

Archicad не обеспечивает изоляции между внешними последовательностями вызовов.

**Требование:** файловый/ОС lock на процесс (singleton) + in-flight guard (ровно **одна** мутация в полёте на весь Router) + идемпотентный intake HTTP.

### B2. HTTP-уровень: успех транспорта не равен ни успеху, ни провалу
Ответ может потеряться при 200 OK (обрыв после применения), при таймауте клиента, при 5xx после применения. Нужна классификация исходов вызова и правило для каждого:

| Исход вызова | Трактовка | Действие |
|---|---|---|
| 200 + тело с GUID | CLAIMED | → read-back |
| 200 + пустое/битое тело | UNKNOWN | → PAUSED(OP_UNKNOWN) |
| 4xx с явным отказом валидации адаптера | NOT_APPLIED (условно) | → PRECHECK_FAILED, без повтора |
| 5xx | UNKNOWN | → PAUSED |
| Timeout | UNKNOWN | → PAUSED |
| Обрыв соединения | UNKNOWN | → PAUSED |

Только первый столбец ведёт к верификации. Всё, что не 200-с-телом, — **остановка**.

### B3. Нет детектора дублей на стороне модели (семантическая идемпотентность)
Даже с идеальным idempotency key: если предыдущий запуск оставил объект **без подтверждения** (UNKNOWN), следующий запуск создаст **второй** объект. Ключ защищает от повторной *отправки*, но не от повторного *намерения*.

**Требование:** `ensure`-семантика перед каждым `create`:
```
1. поиск по маркеру  → найден ровно 1 → ADOPTED, мутация НЕ отправляется, op = VERIFIED
2. поиск по якорю    → найден >0 без маркера → PAUSED(AMBIGUOUS_MATCH)  # возможно, это наследие прошлого запуска
3. не найдено        → create
```
Это единственный способ сделать повторный запуск задания безопасным.

### B4. Delete и компенсирующее удаление — самый опасный путь
Удаление по GUID, взятому из неподтверждённого mapping, — это уничтожение пользовательских данных. Архитектурно delete опаснее create: create обратим удалением, delete обратим только из бэкапа.

**Требование v1:**
- delete разрешён **только** для объектов с `mapping.status == CONFIRMED`, `method ∈ {MARKER_MATCH, ANCHOR_ADOPT}` и `created_by_job == current_job_id`;
- двухфазно: найти по маркеру → сверить количество и свойства → удалить;
- **автокомпенсация запрещена** (см. раздел 8).

### B5. Bulk operations: частичный успех неразличим
Bulk-вызов без per-element результата оставляет модель в неизвестном состоянии, которое нельзя реконсилировать: непонятно, какие из N элементов создались.

**Требование v1:** bulk **запрещён на уровне валидатора** (не «не используем», а отклоняем задание). Если адаптер умеет только bulk — Router разворачивает его в N одиночных операций с индивидуальным read-back; стоимость в латентности признаём ценой v1.

### B6. Операции, зависящие от selection / view state
Всё, что действует «на текущее выделение», запрещено, пока Router сам его не установил и не проверил. Отдельно и менее очевидно: **переключение окна / этажа / комбинации слоёв меняет то, что видит read-back**. Read-back обязан явно задавать фильтр (тип, этаж, слой), а не надеяться на «текущий вид».

Отдельный риск: некоторые команды Archicad блокируют главный поток и ожидают ввода пользователя (например, запрос точки у пользователя — такие команды есть в Tapir). Попадание в такой вызов = зависание Router до вмешательства человека. Такие команды должны быть в чёрном списке.

### B7. Слои: locked / hidden / layer combination / renovation filter
- Элемент на **скрытом** слое → read-back «не найден» → ложный `VERIFY_FAILED`;
- слой **заблокирован** → мутация отклонена с невнятной ошибкой;
- активная **комбинация слоёв** или фильтр реконструкции → элемент не виден, хотя существует.

**Требование:** явное поле `layer` в операции; precheck «слой существует, видим, не заблокирован»; различение вердиктов «не найден» vs «найден, но невидим».

### B8. Отсутствие инварианта счётчиков элементов
См. A8. Выделяю отдельно, потому что это проверка с максимальным соотношением польза/стоимость: считать элементы по типам до и после шага. Ловит двойное создание, создание «не там», кражу GUID, создание мусорного элемента адаптером.

### B9. Верификация — это ассерт в момент времени, а неперманентная истина
Стена, подтверждённая как 12.0 м, afterwards обрезается примыканием другой стены → её `VERIFIED` устарело. Если в конце пакета перепроверять всё → получим ложный mismatch на корректной модели.

**Требование:** различать:
- **per-op verify** — ассерт сразу после создания (геометрия в допуске, маркер, тип, этаж, слой);
- **package-level re-verify** — только инварианты, устойчивые к стыкам: существование по маркеру, тип, этаж, слой, количество. Геометрию на этом уровне не перепроверять;
- явно declared `expect_join: true` — сигнал, что обрезка ожидаема.

### B10. Симметрия и направление: проёмы в локальной системе стены
Проём задаётся в системе координат **стены-хозяина**. При flip стены координата «2.0 м от начала» превращается в «2.0 м от конца» — **симметричная ошибка, которую невозможно обнаружить сравнением чисел**, если не зафиксировано направление.

**Требование:** при создании стены фиксировать её направление (вектор from→to) в job state. Проверка проёма должна либо использовать явный якорь (`from_start` / `from_end`), либо принимать симметричную позицию как допустимую — но **осознанно**, через флаг в `verify_spec`.

### B11. Высота и привязка верха
`height: 3.0` при `top_link = story_up` не хранится как число → read-back вернёт «привязано», а не 3.0 → ложный mismatch. И наоборот: если планировалась привязка, а создалась абсолютная высота — это реальная ошибка, которую надо поймать.

**Требование:** явное поле `top_link: absolute | story_up` и соответствующая ветка проверки.

### B12. Нет таксономии ошибок → recovery не может ветвиться
Без неё recovery — это один обработчик `except Exception`. Минимальный набор (Приложение 2):
`VALIDATION` / `PRECONDITION` / `TOOL_REFUSED` / `TOOL_TIMEOUT` / `TOOL_TRANSPORT` / `VERIFY_FAILED` / `VERIFY_INCONCLUSIVE` / `VERIFY_UNAVAILABLE` / `MODEL_DRIFT` / `AMBIGUOUS_MATCH` / `INSTANCE_MISMATCH` / `LOCK_CONTENTION`.
Каждый класс должен иметь заранее прописанный переход состояния и текст для человека.

### B13. Нет граничных проверок (canary на единицы измерения)
Диапазоны отсекают «ChatGPT перепутал мм и м» ещё на валидации:
```
|coord| ≤ 1e4 м ; 0.05 ≤ length ≤ 500 м ; 0.02 ≤ thickness ≤ 2.0 м ;
0.5 ≤ height ≤ 20 м ; макс. операций в job ; макс. операций в пакете
```
Плюс проверка «все координаты в одном порядке величины» — ловит смешанные единицы внутри плана.

### B14. Семантика повторного запуска job не определена
«Запустить HOUSE_001 ещё раз» — что это?
- job `COMPLETED` + тот же `plan_hash` → **no-op**, вернуть отчёт;
- job не в терминальном состоянии → **отказ**, пока не пройден recovery;
- план изменился → **новый job_id** (никаких «дозаписей» в выполненный job);
- job `QUARANTINED` → только ручная уборка, исполнение заблокировано навсегда.

### B15. Mapping не имеет provenance и не переживает процесс
Mapping — это не `dict[str, str]` в памяти. Это запись:
```
bimexec_id, guid, job_id, op_id, created_at,
method: CREATE_CLAIM | MARKER_MATCH | ANCHOR_ADOPT | RECONCILE_ADOPT,
confirmed_at, verification_snapshot_hash, status, marker_value
```
Без provenance невозможно отличить надёжную привязку (по маркеру) от догадки (по ответу инструмента), а recovery нечем руководствоваться.

### B16. Undo-стек Archicad как общий ресурс
Каждая мутация Router — шаг undo. Сотни шагов → человеку невозможно откатиться. C++ API умеет группировать модификации в один undo scope с человекочитаемым именем, а отмена через `APIERR_CANCEL` откатывает **весь scope** (F4) — но через JSON/MCP это, скорее всего, недоступно.

**Требование v1:** если адаптер даёт undo scope — оборачивать **каждую операцию** scope с именем вида `BIMEXEC PKG02 W_F1_EXT_001 Create wall`. Если нет — задокументировать, что единственный механизм отката в v1 — **ручной Ctrl+Z человеком**, и число шагов равно числу операций. Это влияет на рекомендуемый размер пакета (см. D).

### B17. Read-back может вернуть устаревшие данные
Если читать в том же командном контексте, что и писали, адаптер или Archicad может отдать закэшированное состояние.

**Требование:** мутация и проверка — **разные** вызовы; при наличии явного flush/rebuild/regen — вызывать его; при подозрении на кэш (прочитанное состояние в точности равно до-мутационному при ненулевом ответе инструмента) — вердикт `INCONCLUSIVE`, **не** `FAILED`.

### B18. `mode: "strict"` не определён
Строковый флаг без формального определения — это намерение, а не механизм. `strict` должен означать конъюнкцию:
1. JSON Schema, 2. неизвестные ключи — ошибка, 3. whitelist операций, 4. все ссылки (`depends_on`, `host_wall`) разрешимы, 5. уникальность `id`, 6. граничные проверки, 7. обязательные `units` / `tolerance` / `verify`, 8. capability gating.

Иначе в какой-то момент окажется, что strict был включён, а задание с неизвестным ключом прошло.

## C. Medium-risk issues

| # | Риск | Почему важен |
|---|---|---|
| C1 | Нет версий в схеме (`schema_version`, `bimexec_version`, `adapter_version`, `archicad_version`) | Tapir/BIBIM активно меняются (появляются новые write-команды); без версий невозможно отличить «сломалось» от «изменилось API» (F1) |
| C2 | Нет provenance плана (`source`, `plan_hash`, `created_at`, `confirm_token`) | Нечем доказать, что исполнялось именно то, что одобрил человек |
| C3 | `timeout` / `max_attempts` / `verify_policy` не в схеме, а в коде Router | План и исполнитель рассинхронизируются; «strict» перестаёт быть свойством задания |
| C4 | Dry-run не покрывает ветки UNKNOWN / INCONCLUSIVE / UNAVAILABLE | Synthetic self-tests сейчас, вероятно, гоняют happy path. Нужна инжекция: таймаут, «успех без изменения», дубль, чужой GUID, drift, падение read-back |
| C5 | Нет негативных тестов верификации | Verify должен уметь **Fail**. Тест: испортить модель вручную → ожидаем `VERIFY_FAILED`. Без этого verify никто не проверял |
| C6 | Нет append-only audit trail с хэшами запросов/ответов и таймингами | Пост-мортем первого инцидента будет невозможен |
| C7 | PKG01 STORIES — особая зона риска | Изменение набора/отметок этажей **двигает уже существующие элементы**. Должно быть первым, с precondition «проект пуст или набор этажей совпадает», и проверкой по отметкам, а не по числу этажей |
| C8 | Библиотечные части проёмов | Отсутствующая часть → подстановка/заглушка. Verify обязан сверять **имя библиотечной части**, а не только «проём существует» |
| C9 | Параметры по умолчанию инструмента | Создание через текущие настройки инструмента создаст «что угодно». Все параметры обязаны быть явными; неполный набор → `REJECTED` на валидации, а не «создалось как получилось» |
| C10 | Нет метрик и health-отчёта | Нужны: latency, доля UNKNOWN, доля INCONCLUSIVE, число drift-событий, доля ложных mismatch. Иначе систему будут «настраивать по ощущениям» |
| C11 | Нет владения job (owner token / nonce) | Локальный Router, но устаревший поставленный job не должен исполняться дважды и нельзя «долить» операции в чужой job |
| C12 | Время в журнале | Монотонные sequence numbers + UTC; timestamp как единственный порядок — источник гонок при быстрых переходах |
| C13 | Explicit tool routing не зафиксирован | «Какая op идёт через BIBIM, какая через MCP/Tapir» должно лежать в конфиге с версией, иначе «explicit» останется намерением и разные прогоны пойдут разными путями |
| C14 | Ретраи read-only | Повтор read-back допустим (bounded, экспоненциально), но **не снимает PAUSED автоматически** — только человек снимает |
| C15 | Управленческий риск «верификация мешает» | Как только появятся ложные mismatch, появится соблазн ослабить допуски. Нужна телеметрия ложных срабатываний, чтобы отличать «плохой verify» от «плохая модель» |

## D. Рекомендуемый BIMEXEC v1 state machine

### D1. Job

```
                    ┌──────────────────────────────────────────┐
                    │                                          │
CREATED ──► VALIDATING ──► REJECTED (терминальное)             │
                 │                                             │
                 ▼                                             │
             VALIDATED ──► READY ──► RUNNING ──────────────────┤
                                       │  ▲                    │
                                       ▼  │ resume_token       │
                                     PAUSED(reason)            │
                                       │                       │
                                       ▼                       │
                                  RECONCILING ─────────────────┤
                                       │                       │
                    ┌──────────────────┼───────────────────┐   │
                    ▼                  ▼                   ▼   │
              COMPLETED            FAILED            QUARANTINED
            (терминальное)     (терминальное)       (терминальное)
                    │
                    ▼
                 ABORTED (человек отменил; терминальное)
```

**Обязательные состояния:**
`CREATED`, `VALIDATING`, `VALIDATED`, `REJECTED`, `READY`, `RUNNING`, `PAUSED(reason)`, `RECONCILING`, `COMPLETED`, `FAILED`, `ABORTED`, `QUARANTINED`.

**reason-коды для PAUSED (закрытый список):**

| reason | Что произошло | Кто снимает |
|---|---|---|
| `VERIFY_MISMATCH` | Прочитано, не совпало с `verify_spec` | человек: принять / исправить вручную / abort |
| `VERIFY_INCONCLUSIVE` | Прочитано, данных не хватает для вывода | человек |
| `VERIFY_UNAVAILABLE` | Read-back невыполним (F2 — реальный кейс) | человек |
| `OP_UNKNOWN` | Нет ответа / таймаут / обрыв после отправки мутации | человек (только через reconcile) |
| `MODEL_DRIFT` | Модель изменилась вне BIMEXEC | человек |
| `AMBIGUOUS_MATCH` | Найдено >1 кандидата на привязку | человек |
| `DEPENDENCY_BLOCKED` | Пакет-зависимость в `PARTIAL`/`FAILED` | человек |
| `INSTANCE_MISMATCH` | Другой инстанс/проект Archicad | человек (re-bind) |
| `PRECONDITION_FAILED` | Слой заблокирован, область не пуста и т.п. | человек |
| `WRITE_GATE_CLOSED` | WriteGate выключен / нет confirm_token | оператор |
| `RECOVERY_REQUIRED` | Рестарт Router при нетерминальных операциях | человек (обязателен reconcile) |

> **Ключевое свойство v1:** `PAUSED` — это **не** «пауза и сейчас продолжим». Это состояние, из которого выходят **только** по явному человеческому решению. Никаких автопродолжений, никаких «подождём и попробуем ещё раз».

**Гранулярность пакетов (рекомендация, вытекающая из B16 и из цены PAUSED):**
```
1 пакет = 1 тип элемента + 1 этаж + ≤ 25–50 операций
```
Мелкие пакеты означают: потеря работы при PAUSED мала, resume дешёв, человеку проще откатиться вручную (undo-шагов меньше), зависимость выражается честнее.

### D2. Package

```
PENDING ──► BLOCKED ──► READY ──► PRECHECK ──► RUNNING ──► POSTCHECK ──► COMPLETED
   │           │                      │            │            │
   │           └──► SKIPPED_DEP       │            │            └──► PARTIAL
   │                                  ▼            ▼                   │
   └──► CANCELLED               PRECHECK_FAILED  OP_HALTED            └──► FAILED
```

- `COMPLETED` — **все** операции в `{VERIFIED, ADOPTED, SKIPPED}`.
- `PARTIAL` — есть верифицированные операции, но пакет не завершён. **Не является успехом для зависимых пакетов.**
- `SKIPPED_DEP` — зависимость не выполнена; в v1 это всегда ведёт к `PAUSED(DEPENDENCY_BLOCKED)`, а не к «пропустили и поехали дальше».
- `FAILED` — ни одна операция не верифицирована.

### D3. Operation (самая важная машина состояний)

```
                    ┌─────────────────────────────────┐
                    │                                 │
PLANNED ──► PRECHECK_FAILED ──► REJECTED              │
   │                                                  │
   ├──► DISPATCHED ◄──────────────────────────┐       │
   │        │                                 │       │
   │        ├──► UNKNOWN_TIMEOUT ─────────────┤       │
   │        │                                 │       │
   │        ▼                                 │       │
   │     CLAIMED                              │       │
   │        │                                 │       │
   │        ├──► VERIFY_FAILED ───────────────┤       │
   │        ├──► VERIFY_INCONCLUSIVE ─────────┤       │
   │        ├──► VERIFY_UNAVAILABLE ──────────┤       │
   │        │                                 │       │
   │        ▼                                 │       │
   │     VERIFIED ────────────────────────────┼───────┘
   │                                          │   (все нетерминальные → job PAUSED)
   └──► ADOPTED (найден по маркеру/якорю,      │
        мутация НЕ отправлялась)               │
                                               │
                                          (человек: ADOPT / ABORT / MANUAL)
```

**Определения:**
- `DISPATCHED` — вызов отправлен, исхода нет. **Ключевое состояние.** Из него выходят только через read-back (CLAIMED → верификация) или через reconcile.
- `CLAIMED` — инструмент ответил успешно, есть GUID (возможно). Ещё **не** доказательство.
- `VERIFIED` — и только оно — означает «модель содержит то, что задумано».
- `UNKNOWN_TIMEOUT` — отдельное состояние, а не «ошибка с флагом».
- `ADOPTED` — объект найден при повторном запуске/реконсиляции, новая мутация не отправлялась.

### D4. Шаг исполнения одной операции (алгоритм v1)

```
0. ГЛОБАЛЬНЫЙ GATE
   if в job есть операция в {DISPATCHED, CLAIMED, UNKNOWN_TIMEOUT,
                             VERIFY_INCONCLUSIVE, VERIFY_UNAVAILABLE}:
        halt  # I6 — никаких мутаций, пока есть неопределённость

1. PRECHECK
   - process lock удерживается
   - instance binding перепроверен (port + project info)      → иначе PAUSED(INSTANCE_MISMATCH)
   - fingerprint == сохранённому после прошлого шага          → иначе PAUSED(MODEL_DRIFT)
   - все пакеты из depends_on в status COMPLETED              → иначе PAUSED(DEPENDENCY_BLOCKED)
   - все ссылки на объекты (host_wall) имеют mapping CONFIRMED → иначе PAUSED(DEPENDENCY_BLOCKED)
   - слой существует/видим/не заблокирован; область пуста (если требуется)
   - WriteGate открыт, confirm_token валиден                   → иначе PAUSED(WRITE_GATE_CLOSED)

2. WAL (fsync ДО отправки)
   append(seq, job_id, plan_hash, pkg, op, idempotency_key, request_hash, attempt_no=1, INTENT)

3. ENSURE-ПРОВЕРКА (семантическая идемпотентность)
   - поиск по маркеру → 1 найден + якоря совпали → op = ADOPTED, переход к шагу 9
   - поиск по якорю → >0 без маркера → PAUSED(AMBIGUOUS_MATCH)

4. DISPATCH  (ровно одна попытка, таймаут T_op)
   - не 200 с телом → op = UNKNOWN_TIMEOUT → WAL → PAUSED(OP_UNKNOWN) → STOP

5. WAL
   append(CLAIM, response_hash, guid_claim)

6. MARKER (мутация, требующая собственной проверки)
   set Element ID = "BX:<job_id>:<op_id>:<nonce>"
   - недоступно через адаптер → работать только в режиме "пустая область + уникальный якорь"

7. READ-BACK (отдельный вызов, явные фильтры type/story/layer)
   - по маркеру; если недоступно — по GUID; дополнительно — по якорю

8. VERIFY по verify_spec → OK | FAILED | INCONCLUSIVE | UNAVAILABLE
   - OK → шаг 9
   - остальные → WAL → PAUSED(соответствующий reason) → STOP

9. POSTCHECK
   - count_delta точно равен ожидаемому → иначе PAUSED(VERIFY_FAILED)
   - fingerprint пересчитан и сохранён
   - если адаптер даёт undo scope — закрыть scope

10. COMMIT
   op = VERIFIED, mapping = CONFIRMED (method, snapshot hash)
   WAL append(RESULT), snapshot состояния через atomic rename
```

### D5. Mapping BIMEXEC ID → Archicad GUID: полный жизненный цикл

| Вопрос | Ответ v1 |
|---|---|
| **Когда создаётся** | Запись `PLANNED` создаётся на этапе `VALIDATED` для каждой операции с `id`. GUID появляется как `CLAIMED` из ответа инструмента — **недоверенный**. |
| **Когда считается подтверждённым** | Только после read-back, доказавшего: элемент существует **И** тип совпал **И** этаж совпал **И** слой совпал **И** (маркер совпал **ИЛИ** (якорь совпал **И** кандидат ровно один)) **И** геометрия в declared допуске. Только тогда `CONFIRMED`. |
| **Повторный запуск** | Сначала `ensure`-поиск по маркеру. Найден → `ADOPTED` (новая мутация **не** отправляется). Не найден, но найден якорный кандидат без маркера → `PAUSED(AMBIGUOUS_MATCH)`. Не найдено ничего → create. |
| **Объект есть, GUID неизвестен** | Реконсиляция: поиск по маркеру → по якорю с требованием уникальности. Категорически запрещено: «последний созданный», «первый в выборке», «по индексу», «по текущему выделению». |
| **Исключение привязки к неправильному объекту** | Три уровня: (1) маркер как первичный ключ; (2) проверка якорей type/story/layer/geometry при любом методе привязки; (3) тройная проверка перед **любым** изменением/удалением: GUID → маркер → свойства. |
| **GUID перестал существовать** | `STALE`. Если элемент удалён человеком → `ORPHANED` + `PAUSED(MODEL_DRIFT)`. Автопересоздание запрещено. |

**Состояния mapping:** `PLANNED → CLAIMED → CONFIRMED → STALE | ORPHANED`, плюс метод-альтернативa `ADOPTED`.

## E. Required invariants

Формулируются как проверяемые утверждения. Каждый инвариант обязан иметь тест.

| # | Инвариант |
|---|---|
| **I1** | Ни одна мутация не отправляется без записи `INTENT` в WAL, причём WAL записан и сброшен на диск **до** отправки. |
| **I2** | У каждой операции уникальный `idempotency_key`; для мутирующих операций `attempt_no == 1` всегда; не более одной отправки на ключ. |
| **I3** | В любой момент времени во всём Router **не более одной** мутации в полёте; процесс-Router существует в единственном экземпляре. |
| **I4** | Автоматический повтор мутирующего вызова **запрещён** при любом исходе. Повтор read-only вызовов разрешён, bounded. |
| **I5** | HTTP/tool success ≠ доказательство. Статус `VERIFIED` достижим **только** через read-back по `verify_spec`. |
| **I6** | Ни одна мутация не выполняется, пока в job есть операция в `DISPATCHED`, `CLAIMED`, `UNKNOWN_TIMEOUT`, `VERIFY_INCONCLUSIVE` или `VERIFY_UNAVAILABLE`. |
| **I7** | Зависимость пакета удовлетворена **только** при `status == COMPLETED`. `PARTIAL` не удовлетворяет. |
| **I8** | `mapping.CONFIRMED` возможен только при доказательстве по маркеру или по уникальному якорю + совпадению type/story/layer/geometry в declared допуске. |
| **I9** | Запрещена привязка к элементу, существовавшему до job, кроме как через явный `ADOPT` с доказательством по маркеру или доказательством уникальности. Привязка по «последнему созданному» / индексу / выделению запрещена. |
| **I10** | Fingerprint на PRECHECK шага равен сохранённому; дельта счётчиков на POSTCHECK точно равна `count_delta`. |
| **I11** | Каждая мутирующая операция адресуется явным GUID (или якорем, разрешённым в том же шаге). Операции, зависящие от текущего выделения, запрещены. |
| **I12** | `plan_hash` иммутабелен в течение жизни job. Расхождение → `REJECTED`. |
| **I13** | Instance binding перепроверяется перед каждым мутирующим вызовом. Расхождение → `PAUSED(INSTANCE_MISMATCH)`. |
| **I14** | Вердикты верификации — ровно `OK / FAILED / INCONCLUSIVE / UNAVAILABLE`. Продолжение разрешено **только** при `OK`. `INCONCLUSIVE` и `UNAVAILABLE` не означают ни успеха, ни провала. |
| **I15** | Единицы, начало координат, datum и допуски declared в плане; неявных дефолтов нет; граничные проверки применяются на `VALIDATE`. |
| **I16** | `bulk`, `delete`, `move`, `rotate` и selection-зависимые операции — вне scope v1 и **отклоняются валидатором**, а не «не используются». |
| **I17** | Каждый переход состояния записан в journal до того, как эффект становится наблюдаемым извне. |
| **I18** | После рестарта Router: любая нетерминальная операция → `PAUSED(RECOVERY_REQUIRED)`; ни одна мутация до принятия отчёта реконсиляции человеком. |
| **I19** | Fail-closed: неизвестный класс ошибки = остановка. Неизвестное ≠ успешное. |
| **I20** | `job.COMPLETED` достижимо только если все операции терминальны в `{VERIFIED, ADOPTED, SKIPPED}` и нет ни одного `UNKNOWN`. |
| **I21** | План не мутирует после `VALIDATED`. Изменение = новый job. |
| **I22** | Никакая строка из плана не становится именем инструмента, параметром запроса или исполняемым выражением без прохождения через whitelist-валидатор. У Router нет кодового пути, в котором вывод LLM достигает исполнения минуя валидатор. |

### Операционная подготовка (выполняется человеком, вне BIMEXEC)

- Базовое состояние файла сохраняется **человеком штатными средствами Archicad**; Router не инициирует сохранение, запись или модификацию PLN — это вне scope по принятому решению.
- Все прогоны — **только** в одноразовом проекте-песочнице, не в рабочем PLN.
- Archicad запущен в одном экземпляре, человек не трогает мышь/клавиатуру во время прогона (это отдельно проверяется тестом T6).

### Программа первого write-теста

Каждый шаг — отдельный прогон, без «починить на ходу».

| # | Тест | Критерий успеха |
|---|---|---|
| **T0** | Dry-run на полном плане дома (реальные объёмы) | 0 мутаций; отчёт по capability; все `OUT_OF_SCOPE` выявлены |
| **T1** | Одна стена на пустом этаже: create → marker → read-back | mapping `CONFIRMED`, count_delta = 1, journal полный |
| **T2** | 4 стены замкнутого контура + T-стык + примыкание | **0 ложных mismatch**; ≥1 ложного → `verify_spec` не готов, назад к F-9 |
| **T3** | Пакет с зависимостью: PKG01 (stories) → PKG02 → PKG04 (проём в стене) | PKG04 стартует только после `PKG02.COMPLETED`; проём привязан к правильной стене (проверка вручную) |
| **T4** | Инжекция таймаута: оборвать соединение **после** применения | `PAUSED(OP_UNKNOWN)`; в модели ровно 1 стена; повторов нет; после рестарта reconcile предлагает `ADOPT` |
| **T5** | `kill -9` Router между dispatch и verify | то же, что T4 |
| **T6** | Инжекция drift: человек подвинул стену мышью между операциями | `PAUSED(MODEL_DRIFT)` |
| **T7** | Эмуляция недоступного read-back (F2) | `PAUSED(VERIFY_UNAVAILABLE)`, **не** продолжение |
| **T8** | Тройная повторная отправка того же job по HTTP | ровно 1 dispatch; ответы содержат текущий статус; дублей нет |
| **T9** | Негативный тест: подменить ожидаемую геометрию | `VERIFY_FAILED` (verify умеет падать) |

**Go/no-go критерии выхода из песочницы:** 0 orphan-элементов; 100% mapping в `CONFIRMED`/`ADOPTED` с provenance; journal без пропусков seq; `count_delta` совпал во всех прогонах; T0–T9 зелёные; нет ни одного случая автопродолжения после неопределённости.

## G. Что можно оставить на v2

| Направление | Почему не v1 |
|---|---|
| **Компенсирующие действия и автоматический rollback** | Требуют настоящей границы транзакции (`ACAPI_CallUndoableCommand` с cancel-откатом, F4), которая через JSON/MCP, скорее всего, недоступна. В v1 откат = человек + Ctrl+Z |
| **Delete / move / rotate как полноценные операции** | Обратимость хуже, чем у create; требуют двухфазной адресации и зрелого mapping |
| **Bulk-операции с per-item результатом** | Сейчас bulk не даёт per-element статуса → нереконсилируемое состояние |
| **Объектные зависимости (`depends_on` на operation/object)** | В v1 достаточно зависимостей на пакетах + ссылок `host_wall` внутри операции. Планировщик с топологией на объектах — лишняя сложность |
| **Параллельное исполнение пакетов** | Один Archicad, один оператор, один undo-стек. Параллелизм здесь не даёт выигрыша и ломает single-flight |
| **`ensure_*` upsert-семантика («обеспечить состояние»)** | Идемпотентный «создай или обнови» требует устойчивого сопоставления существующих элементов — это v2 после накопления статистики по якорям |
| **Автопредложения recovery-решений** | В v1 человек принимает решение по отчёту; автоматизация предложений — после набора статистики |
| **Семантическая верификация** (экспорт свойств/IFC и сверка) | В v1 достаточно геометрии + типа + этажа + слоя + маркера + count_delta |
| **Крыши, зоны, лестницы, сложные перекрытия, профили, композиты, фавориты, классификации, renovation status** | Расширение области после стабилизации ядра |
| **Re-планирование и диффинг планов (plan v2 поверх существующей модели)** | Требует `ensure`-семантики |
| **Undo-group на уровень пакета** | Требует доступности undo scope через адаптер |
| **Мульти-инстанс и Teamwork/BIMcloud** | Радикально меняет модель блокировок и идемпотентности |
| **Сохранение PLN** | Сознательно вне scope по принятому решению; остаётся штатной процедурой Archicad/человека |

## Приложение 4. Процедура реконсиляции (read-only)

```
1. Lock + загрузка journal. Никаких мутаций.
2. Instance binding: совпал ли инстанс/проект с сохранённым?
   нет → PAUSED(INSTANCE_MISMATCH), человек делает re-bind или abort.
3. Fingerprint модели. Сравнить с сохранённым в journal.
4. Для КАЖДОЙ операции в {DISPATCHED, CLAIMED, UNKNOWN_TIMEOUT}:
   a. поиск по маркеру BX:<job>:<op>:<nonce>
      1 найден + якоря совпали   → APPLIED_VERIFIABLE   → предложить ADOPT
      1 найден + якоря НЕ совпали→ APPLIED_BUT_MISMATCH → предложить PAUSED/ручную уборку
      >1 найден                  → AMBIGUOUS            → предложить PAUSED
   b. маркер недоступен → поиск по GUID (если есть claim)
      найден + якоря совпали     → APPLIED_VERIFIABLE   → предложить ADOPT
      найден + не совпали        → APPLIED_BUT_MISMATCH
      не найден                   → NOT_APPLIED (осторожно: см. ниже)
   c. якорный поиск по геометрии:
      >0 кандидатов без маркера  → SUSPECTED_ORPHAN     → предложить ручную уборку
5. Сформировать отчёт: по каждой операции — класс, найденные GUID, расхождения.
6. Человек выбирает: RESUME_FROM_BOUNDARY | ADOPT_ALL_VERIFIABLE |
                     MANUAL_CLEANUP | ABORT | QUARANTINE.
7. Только после принятого решения — перевод в RUNNING или терминальное состояние.
```

**Осторожность про `NOT_APPLIED`:** «не найден по GUID» **не** доказывает, что мутация не применена — она могла примениться и получить другой GUID, или примениться на другом этаже/слое. `NOT_APPLIED` — это гипотеза, которая подтверждается только отсутствием кандидатов и при якорном поиске, и при совпадении `count_delta` с до-мутационным состоянием. При любых сомнениях — `AMBIGUOUS`, дальше человек.

## Итоговая оценка зрелости

| Компонент | Текущий статус | Вердикт |
|---|---|---|
| Разбиение JOB/PACKAGE/OPERATION | Есть | Концепция верна; требует +7 обязательных полей и объекта `verify` |
| Идемпотентность | DuplicateMutationGuard | Недостаточно: нужен персистентный ключ + таблица отправок + `ensure`-семантика |
| Read-back verification v1 | Есть | Нужны 4 вердикта, `verify_spec` в плане и capability gating |
| Mapping ID → GUID | Декларирован | Критически недоработан: нужен жизненный цикл из 5 состояний + маркерная привязка |
| Dependency engine | `depends_on` | Нужен детектор циклов, проверка существования, семантика `PARTIAL`, порядок исполнения |
| Fail-closed recovery | Есть | Нужна реконсиляция по Приложению 4 и `PAUSED(RECOVERY_REQUIRED)` как обязательное состояние |
| Транзакции / компенсации | Нет | Осознанно в v2; в v1 — ручной откат человеком |
| Готовность к реальному write | — | **Нет.** После P0-чеклиста (14 пунктов) и T0–T9 — да, в ограниченной области (только create + узкий change) |
