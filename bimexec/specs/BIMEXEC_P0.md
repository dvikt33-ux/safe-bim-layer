## 2. Missing blockers

### 2.1 Блокаторы, без которых решения 1 и 8 физически не работают

**M1. Нет WAL (write-ahead journal) до dispatch.** Это самое важное отсутствие во всём списке. Решение 1 постулирует UNKNOWN, решение 8 — реконсиляцию. Но **что отличает «никогда не отправляли» от «отправили, исход неизвестен»?** Только запись, сделанная **до** отправки. Без неё после краха Router видит операцию в `PLANNED` и не знает, можно ли её отправлять. Отправит — получит дубль (мутация-то могла примениться). Не отправит — задание нельзя продолжить.

```
ДО вызова:   WAL.append(INTENT, seq, job, run, object_id, nonce, idempotency_key, request_hash, attempt=1) → fsync
ПОСЛЕ ответа: WAL.append(OUTCOME, response_hash, candidate_guid)
```
Стоимость — один fsync на мутацию. Без этого весь P0 держится на догадке.

**M2. Нет single-flight и singleton процесса.** Формулировка «после UNKNOWN запрещены любые новые mutating calls по этому job» невыполнима, если:
- второй HTTP-запрос с тем же job пришёл параллельно;
- в очереди стоит другой job (он продолжит писать в тот же Archicad);
- запущен второй процесс Router (dev + prod, или рестарт при живом старом).

Правило v1: **ровно одна мутация в полёте на весь Router**, процесс-Router в единственном экземпляре (ОС-lock). Побочный выигрыш: при single-flight после краха **не более одной** операции в UNKNOWN — recovery становится тривиальным.

**M3. Нет персистентного idempotency key.** `DuplicateMutationGuard` закрывает повтор в рамках живого процесса, но не закрывает: рестарт, повторную доставку HTTP, повторную отправку задания ChatGPT. Ключ должен быть персистентным и content-derived, а не от времени:
```
idempotency_key = H(job_id, run_id, object_id, attempt_no)   # attempt_no = 1 для мутаций, всегда
```

### 2.2 Дыры в принятых решениях

**M4. `NOT_APPLIED` нельзя получать из dispatch-слоя.** Между APPLIED и NOT_APPLIED нет симметрии:
- `UNKNOWN` детектируется тривиально (любой сбой);
- `NOT_APPLIED` — это **утверждение**, которое надо доказать, и ошибочное доказательство ведёт к дублю.

«Инструмент вернул 4xx» не доказывает, что модель не изменилась. «Таймаут» тем более. Поэтому:

> Из dispatch-слоя допустим **только** `UNKNOWN`. `NOT_APPLIED` — это **гипотеза, которую выносит реконсиляция**, и только при положительном доказательстве: маркер не найден **И** якорный поиск пуст **И** `count_delta == 0` **И** read-back backend подтверждённо работоспособен в момент проверки (иначе это `UNAVAILABLE`, а не `NOT_FOUND`).

Практическая польза: состояние `NOT_APPLIED` остаётся в модели (оно нужно для resume), но перестаёт быть «зелёным светом на повтор».

**M5. Запись маркера — отдельная мутация со своим UNKNOWN.** В алгоритме пункта 3 шаг «записать marker» нарисован как детерминированный. Он не детерминирован:
- `SetPropertyValuesOfElements` падает с `Teamwork Permission Denied` на Solo-проекте (E2);
- write может вернуть успех и **не записать** значение (E3);
- соединение может оборваться между применением и ответом.

Значит нужен отдельный узел `MARKER_WRITING` с исходами `BOUND` / `MARKER_UNKNOWN` / `CREATED_UNBOUND`. И отдельная ветка реконсиляции: при `MARKER_UNKNOWN` элемент может существовать **и с маркером, и без** — искать надо и по маркеру, и по candidate GUID.

**M6. Не определён носитель маркера и побочный эффект на модель.** E1 говорит, что Element ID писать можно, но:
- Element ID — **пользовательские данные**, он попадает в ведомости и марки. Запись туда `BX:...` меняет видимое содержание проекта;
- конфликты Element ID случаются (E4);
- предпочтительнее **выделенное строковое свойство** (`BIMEXEC_MARKER`), если адаптер даёт запись user-defined property.

Рекомендация: capability matrix должна эмпирически ответить «что доступно» в порядке приоритета: (1) user-defined property, (2) Element ID. Маркер пишется туда, где **подтверждён round-trip**. Выбор фиксируется в job state, потому что от него зависит процедура реконсиляции.

**M7. Поиск по маркеру должен поддерживать два режима.** Сейчас маркер = `BX:<job>:<object-id>:<nonce>`. Нужен поиск:
- **точный** — по полной строке с nonce (основной путь привязки);
- **по префиксу** — `BX:<job>:<object-id>:*`, без nonce.

Зачем второй: если предыдущий запуск ушёл в UNKNOWN на шаге записи маркера, в модели может лежать элемент с **другим** nonce того же object-id. Точный поиск его не найдёт и создаст дубль. Префиксный поиск найдёт два элемента → `AMBIGUOUS_MATCH` → PAUSED. Это ровно тот случай, который вся система и должна ловить.

**M8. `verify_spec` обязан иметь обязательный минимум из конфига Router, а не из плана.** Самая опасная дыра пункта 4: если `verify_spec` полностью авторство LLM, то план с
```json
"verify": {}
```
или с `"verify": {"type": "wall"}` даст `VERIFIED_OK` на пустом или тривиальном множестве проверок. Формально всё честно: Router «не придумывал критерии», он выполнил то, что сказали.

> Правило: у каждого op-типа есть **mandatory floor** проверок в конфиге Router (не в плане). План может его **расширить**, но не сузить. Пустой или отсутствующий `verify` → `REJECTED` на валидации.

Минимальный floor для `create_wall`: `exists`, `type`, `story`, `layer`, `marker_exact`, `count_delta`, `geometry` (длина + середина + угол по референсной линии).

**M9. Принятый verify_spec не проверяет позицию — стена «не там» пройдёт проверку.** Пример из пункта 4:
```json
"verify": { "type": "wall", "story": 0, "height": {...3.0...}, "thickness": {...0.38...} }
```
Проверяется высота и толщина, но **ничего не проверяет, где стоит стена**. Стена, созданная в другом месте, с другим направлением или на другом этаже, пройдёт этот verify. Плюс `story: 0` — это индекс, что независимо подтверждается багом Tapir с `SetStories` (E5).

Исправленный минимум (позиция обязательна):
```json
"story": { "name": "Ground Floor", "elevation": 0.0 },
"verify": {
  "type": "wall",
  "story": { "name": "Ground Floor", "elevation": 0.0 },
  "layer": "A-WALL-EXTR",
  "marker": { "exact": "BX:HOUSE_001:W_F1_EXT_001:<nonce>" },
  "ref_line": { "from": [1.5, 2.5], "to": [6.5, 2.5], "tolerance_m": 0.01 },
  "length":   { "expected": 5.0, "tolerance_m": 0.05 },
  "height":   { "expected": 3.0, "tolerance_m": 0.001 },
  "thickness":{ "expected": 0.38, "tolerance_m": 0.001 },
  "count_delta": { "Wall": 1 }
}
```

**M10. Нет `count_delta` — самого дешёвого детектора дублей.** Счётчик элементов по типу до/после мутации должен совпасть **точно**. Одна эта проверка ловит: двойное создание, создание «не там», кражу GUID, мусорный элемент от адаптера. Она стоит один read-вызов и не зависит ни от геометрии, ни от допусков. Добавить в mandatory floor каждой операции.

**M11. Instance binding ≠ дрифт состояния. Второго нет вообще.** Пункт 7 привязывает job к инстансу, но не защищает от того, что модель **изменилась внутри того же инстанса**: человек подвинул стену, нажал Ctrl+Z, переключил слой. А это ровно то, что ломает dependent operations (проём уедет в другое место при корректном mapping).

Два разных механизма:
- **identity fingerprint** (кто это) — `projectPath + projectName + isUntitled + isTeamwork + stories(имя+отметка) + archicad_version`. Важно: **не** включает счётчики элементов, иначе он будет меняться от наших же мутаций;
- **state fingerprint** (что изменилось) — счётчики по типам + хэш состояния слоёв; проверяется на PRECHECK каждого шага и перебазируется на POSTCHECK с ожидаемой дельтой.

Порт — это **адрес**, не идентичность: он меняется при рестарте и может достаться другому инстансу. Хранить как адрес, идентичность строить на fingerprint.

**M12. Нет `plan_hash` / иммутабельности плана.** Без него возможно смешивание версий плана внутри job и невозможна безопасная реконсиляция (неизвестно, к какой версии плана относятся найденные элементы). Плюс: job_id + run_id — см. M15.

### 2.3 Отсутствующие проверки

**M13. Независимость read-back не зафиксирована.** Принцип, без которого `VERIFIED_OK` можно получить из одной и той же ошибки дважды:

> Read-back обязан подтверждаться **минимум двумя независимыми путями**, и они должны согласовываться: (1) по GUID из candidate; (2) по маркеру; (3) по фильтру тип+этаж+слой. Ни один из путей не должен переиспользовать ответ create-вызова.

Для стены возможны четыре независимых пути (E6): `GetElementsByType('Wall')`, `GetDetailsOfElements` (геометрия, высота, толщина, слой, этаж), property API (маркер), счётчик элементов. Расхождение путей → `INCONCLUSIVE`, не `VERIFIED_OK`.

**M14. Нет orphan registry.** Решение 10 («не откатываем автоматически») правильно, но в текущем виде означает, что элементы в состоянии `CREATED_UNBOUND` / `BOUND + VERIFIED_FAILED` остаются в модели **без следа**. Нужен реестр: `object_id, candidate_guid, story, layer, час, причина, статус уборки` + отчёт для ручной уборки человеком. Без него «без компенсаций» превращается в «тихо копим мусор в проекте пользователя».

**M15. Не разделены resume и новый run.** Маркер содержит `job_id`, поэтому повторный запуск `HOUSE_001` **найдёт маркеры от прошлого запуска** и всё усыновит (`ADOPTED`). Это правильно для resume после PAUSED, но **неправильно**, если человек вручную почистил модель и хочет строить заново — он получит «всё уже создано», а в модели пусто.

Правило: есть `job_id` (логический) и `run_id` (экземпляр исполнения). Маркер = `BX:<job_id>:<run_id?>…` — не обязательно в строке, достаточно хранить `run_id` в mapping и требовать совпадения при усыновлении. Возобновление возможно **только** как явный `resume(run_id)`; любой другой старт = новый `run_id`, и усыновление чужого `run_id` запрещено (→ `AMBIGUOUS_MATCH`).

**M16. Не зафиксирован отказ биндиться к неподходящему проекту.** Дополнение к пункту 7: `isUntitled == true` → отказ (нет projectPath → идентичность нестабильна); `isTeamwork == true` → отказ в v1 (иная модель блокировок + баг E2 родом оттуда).

**M17. Revalidate binding — сам вызов может упасть.** Если проверка биндинга не выполнима (таймаут, сбой), это **не** «наверное всё ещё тот же инстанс». Это `UNKNOWN` → halt.

**M18. Нет whitelist read-only вызовов в PAUSED.** Решения 1 и 8 останавливают мутации, но реконсиляции нужны read-вызовы. Нужен явный whitelist: во время `PAUSED` / `PAUSED_RECOVERY` разрешён ровно этот список, всё остальное блокируется на уровне диспетчера инструментов (а не «на честном слове»).

**M19. Нет бюджета таймаута и классификации транспорта.** Для каждого вызова: `T_op`, и исходы `200+тело` / `4xx-pre-dispatch` / `5xx` / `timeout` / `обрыв` / `200 с битым телом`. Только первый ведёт к верификации, остальные → `UNKNOWN`.

**M20. Единицы, базис и `reference_line` / `top_link` отсутствуют в схеме.** `from/to` без reference_line даёт ошибку в половину толщины; `height` при привязке верха к этажу не читается как число → ложный `VERIFIED_FAILED`. Обязательные поля схемы: `units`, `origin`, `elevation_datum`, `reference_line`, `base_level`, `top_link`.

### 2.4 Мелкие, но обязательные

**M21. UNSUPPORTED — в основном validation-time, не runtime.** Статус оставляем, но правило: `verify_spec ∩ capability == sufficient set` проверяется **на валидации**. UNSUPPORTED в рантайме = расхождение capability matrix с реальностью = PAUSED **и** пометка матрицы как недоверенной (в AC29 это реально, см. базовый аудит F2).

**M22. Capability matrix: +5 инфраструктурных строк.** Помимо полей операции нужны: запись маркера (какой носитель, подтверждён ли round-trip), поиск по маркеру (точный/префиксный), read-back по GUID, read-back по фильтру тип+этаж+слой, подсчёт элементов по типу. Без них весь binding-протокол невыполним, а это инфраструктура, а не поля конкретной операции.

**M23. Реконсиляция — read-only by construction.** Отдельный код-path с жёстким запретом мутирующих имён инструментов, а не флаг «не писать». Иначе рано или поздно reconcile попытается «исправить» и станет вторым исполнителем.

## 3. Overengineering / что отложить даже из этого списка

| # | Что убрать/упростить | Почему |
|---|---|---|
| **D1** | `NOT_APPLIED` как исход dispatch-слоя | Убрать. Оставить как гипотезу реконсиляции (M4). Упрощает dispatch до двух исходов: «есть ответ с телом» / «UNKNOWN» |
| **D2** | Bind-token, записываемый в проект | Не нужно. Это дополнительная **запись** в пользовательский проект ради идентичности. Достаточно read-only fingerprint (M11) + отказ биндиться к untitled (M16) |
| **D3** | DSL для `verify_spec` | Не нужно. Фиксированный whitelist имён проверок + обязательный floor из конфига (M8). План передаёт значения и допуски, не логику |
| **D4** | Планировщик и топологическая сортировка | Не нужно при последовательном исполнении. Требовать, чтобы массив `packages[]` **уже** был в топологическом порядке, и валидировать: каждая ссылка `depends_on` указывает на пакет **раньше** в массиве. Проще и предсказуемее |
| **D5** | Re-verify всей геометрии в конце пакета | Не нужно и вредно: стены обрезаются в стыках → ложные `VERIFIED_FAILED` на корректной модели. На границе пакета проверять только `count_delta` и существование по маркерам |
| **D6** | Автоматическая уборка orphan | Нет (решение 10). Только реестр + отчёт человеку (M14) |
| **D7** | Полные snapshot'ы геометрии для каждого элемента | Хранить хэш наблюдения, а не данные. Полные данные — в journal, если нужен пост-мортем |
| **D8** | Поддержка нескольких инстансов Archicad | v1 — один инстанс, один проект, один оператор |
| **D9** | Исчерпывающая capability matrix на все типы элементов | Только op-типы в scope v1. Всё остальное = `OUT_OF_SCOPE` по умолчанию и отбрасывается на валидации |
| **D10** | Отдельный статус для «усыновлено по якорю» | Свести к `ADOPTED` с полем `method`. Не множить состояния ради симметрии |

**Итог по разделу:** из 12 решений **8 принимаются практически как есть**, 4 требуют правок (1, 2, 3, 4), и **добавляется 3 инфраструктурных блокатора** (WAL, single-flight, idempotency key), без которых принятые решения не работают.

## 4. Corrected state machines

### 4.1 Job

```
CREATED ──► VALIDATING ──► REJECTED  (терминальное)
                 │
                 ▼
             VALIDATED ──► BINDING ──► BOUND ──► READY ──► RUNNING ──┐
                                                    ▲               │
                                                    │               ▼
                                                    │          PAUSED(reason)
                                                    │               │
                                                    │               ▼
                                                    └──────── RECONCILING
                                                                   │
                                        ┌──────────────────────────┼──────────────────┐
                                        ▼                          ▼                  ▼
                                    COMPLETED                   FAILED          QUARANTINED
                                  (терминальное)             (терминальное)     (терминальное)
                                                                                 │
                                                                            ABORTED
```

`BINDING` выделен в отдельное состояние — привязка к инстансу это однократный акт с доказательством, а не подразумеваемая предпосылка.

| reason | Источник |
|---|---|
| `OP_UNKNOWN` | нет ответа / таймаут / обрыв / битое тело после dispatch (решение 1) |
| `MARKER_UNKNOWN` | исход записи маркера неизвестен (M5) |
| `CREATED_UNBOUND` | элемент создан, привязка недоказуема (решение 2) |
| `VERIFIED_FAILED` | прочитано, противоречие обязательной проверке |
| `INCONCLUSIVE` / `UNAVAILABLE` / `UNSUPPORTED` | см. решение 5 |
| `AMBIGUOUS_MATCH` | найдено >1 (решение 3) |
| `INSTANCE_MISMATCH` | fingerprint инстанса/проекта разошёлся (решение 7) |
| `MODEL_DRIFT` | state fingerprint разошёлся (M11) |
| `DEPENDENCY_BLOCKED` | пакет-зависимость не в COMPLETED (решение 9) |
| `PRECONDITION_FAILED` | слой заблокирован/невидим, область не пуста, untitled-проект |
| `RECOVERY_REQUIRED` | рестарт Router при нетерминальных операциях (решение 8) |

**Из любого PAUSED выход — только по явному решению человека.** Никаких автопродолжений.

### 4.2 Package

```
PENDING ──► BLOCKED ──► READY ──► RUNNING ──► COMPLETED
   │                       │          │
   │                       │          ├──► PARTIAL  (есть верифицированные op, пакет не завершён)
   │                       │          └──► HALTED   (остановлен из-за PAUSED job)
   │                       │
   │                       └──► PRECHECK_FAILED
   └──► SKIPPED_DEP
```

- `COMPLETED` — все операции терминальны в `{VERIFIED_OK, ADOPTED, SKIPPED}`.
- **`PARTIAL` не удовлетворяет зависимость** — зависимые пакеты уходят в `BLOCKED`, job в `PAUSED(DEPENDENCY_BLOCKED)`.
- Пакет — точка возобновления: состояние персистируется на границе пакета (решение 11).

### 4.3 Operation

Ключевое исправление: **слой исхода вызова и слой верификации разделены**, и узел записи маркера имеет собственный UNKNOWN.

```
                       ┌─────────────────────────────────────────────┐
                       │   (любое «вниз-влево» = job PAUSED + halt)  │
                       └─────────────────────────────────────────────┘

PLANNED
   │  precheck (binding, drift, deps, layer, область)
   ├──► PRECHECK_FAILED ─────────────────────────────► PAUSED(PRECONDITION_FAILED)
   │
   │  WAL: INTENT (fsync)                       ← M1, до dispatch
   ▼
DISPATCHED ──── нет ответа/5xx/обрыв/битое тело ──► UNKNOWN ──► PAUSED(OP_UNKNOWN)
   │
   │  200 + тело: candidate GUID  →  mapping = CANDIDATE   (не доверяем, решение 2)
   ▼
APPLIED_UNVERIFIED
   │  tag-guard: type + story + layer совпали?   ← дешёвая защита от тегирования чужого элемента
   ├──► нет ──► CREATED_UNBOUND ─────────────────► PAUSED(CREATED_UNBOUND)
   │
   │  WAL: MARKER_INTENT
   ▼
MARKER_WRITING ──── нет ответа/сбой ──► MARKER_UNKNOWN ──► PAUSED(MARKER_UNKNOWN)     ← M5
   │
   │  round-trip: прочитан маркер == записанному (строковое равенство)    ← E3
   ├──► нет ──► CREATED_UNBOUND ─────────────────► PAUSED(CREATED_UNBOUND)
   ▼
BOUND  (mapping = CONFIRMED)
   │
   │  verify_spec: ≥2 независимых пути read-back, все обязательные проверки OK   ← M13
   ├──► VERIFIED_FAILED ──► PAUSED(VERIFIED_FAILED)
   ├──► INCONCLUSIVE    ──► PAUSED(INCONCLUSIVE)
   ├──► UNAVAILABLE     ──► PAUSED(UNAVAILABLE)
   ├──► UNSUPPORTED     ──► PAUSED(UNSUPPORTED) + инвалидация capability matrix
   ▼
VERIFIED_OK ──► postcheck: count_delta точно совпал (иначе VERIFIED_FAILED) ──► COMMIT
```

Отдельные ветви:
- `PLANNED ──(ensure: маркер найден, якоря совпали)──► ADOPTED` — мутация **не** отправляется.
- `UNKNOWN ──(реконсиляция: маркер+якоря найдены)──► ADOPTED` — разрешено человеком.
- `UNKNOWN ──(реконсиляция: доказано отсутствие)──► NOT_APPLIED_ASSERTED` — разрешено человеком, затем можно повторить **вручную**.
- `UNKNOWN ──(реконсиляция не дала ответа)──► UNKNOWN_REMAINS` → `QUARANTINED`.

**Три правки к алгоритму пункта 3:**
1. **Маркер пишется до полной верификации, а не после.** Причина: `BOUND + VERIFIED_FAILED` — это находимый объект (чистка возможна), а `CREATED_UNBOUND + VERIFIED_FAILED` — нет. Связывание (identity) и верификация (correctness) — разные вопросы; identity должна быть установлена первой, чтобы любой последующий провал оставлял **находимый** след.
2. **Перед записью маркера — tag-guard** (type + story + layer). Защита от тегирования чужого элемента, если `create` вернул неверный GUID (решение 2 прямо говорит, что GUID не доверенный — но тогда и тегировать по нему blindly нельзя).
3. **Запись маркера имеет собственный UNKNOWN** (M5).

### 4.4 Mapping

```
                    ┌──────────────────► CREATED_UNBOUND ──► ORPHAN
                    │                     (есть candidate GUID,
                    │                      привязка недоказуема)
UNBOUND             │
   │  create вернул GUID
   ▼                    
CANDIDATE ──► MARKER_PENDING ──► CONFIRMED ──► STALE ──► ORPHAN
   │                                 ▲            (guid не резолвится /
   │                                 │             маркер не совпал при revalidate)
   │                                 │
   └──► ADOPTED ─────────────────────┘   (усыновление по маркеру при resume/reconcile;
                                          method = RECONCILE_MARKER | ENSURE_MARKER)
```

| Состояние | Смысл | Читаемо другими операциями |
|---|---|---|
| `UNBOUND` | GUID неизвестен | нет |
| `CANDIDATE` | GUID из create-response, недоверенный | **нет** |
| `MARKER_PENDING` | маркер записан, round-trip не подтверждён | **нет** |
| `CONFIRMED` | round-trip маркера доказан + якоря совпали | **да** |
| `ADOPTED` | найден по маркеру без dispatch в этом run | **да** |
| `CREATED_UNBOUND` | элемент вероятно существует, привязка недоказуема | **нет** |
| `STALE` | было CONFIRMED, GUID/маркер перестал подтверждаться | **нет** |
| `ORPHAN` | элемент удалён или job заброшен; запись для реестра уборки | нет |

**Инвариант читаемости:** ссылка `host_wall` (и любая другая) резолвится **только** в `CONFIRMED` или `ADOPTED`. Плюс дешёвая revalidate (GUID существует + маркер совпадает) перед каждым **использованием** mapping — переход в `STALE` при расхождении.

## 5. Minimal invariants

14 штук. Помечены ★ — **неreducible пятёрка**: если делать абсолютный минимум, делайте эти.

| # | Инвариант |
|---|---|
| **I1** ★ | Ни одна мутация не отправляется без записи `INTENT` в WAL, сброшенной на диск **до** отправки. |
| **I2** ★ | Мутирующий вызов **никогда** не повторяется автоматически; `attempt_no == 1` всегда; не более одной мутации в полёте на весь Router; процесс-Router в единственном экземпляре. |
| **I3** ★ | Любой `UNKNOWN` (dispatch или запись маркера) и любой вердикт ≠ `VERIFIED_OK` останавливают **все** мутации в job до явного решения человека. |
| **I4** ★ | Ответ create **не является доказательством**: GUID из него — всегда `CANDIDATE`. Единственный путь в `CONFIRMED` — round-trip маркера, подтверждённый независимым чтением. |
| **I5** ★ | `VERIFIED_OK` выставляется только если **все** обязательные проверки прошли, причём проверки подтверждены **минимум двумя независимыми путями** read-back, не переиспользующими ответ create. |
| **I6** | `verify_spec` обязателен, содержит mandatory floor из конфига Router, согласован с параметрами операции и со capability matrix; пустой/отсутствующий → `REJECTED` на валидации. |
| **I7** | `count_delta` после каждой мутации совпадает **точно**; расхождение → `VERIFIED_FAILED`. |
| **I8** | Identity- и state-fingerprint перепроверяются перед каждой мутацией; расхождение или **невозможность проверки** → halt. |
| **I9** | Mapping читаем другими операциями только в `CONFIRMED` / `ADOPTED`; привязка по «последнему созданному», индексу или выделению запрещена. |
| **I10** | Каждый элемент в `CREATED_UNBOUND`, `MARKER_UNKNOWN` или `BOUND + не-OK` регистрируется в orphan registry. Автоматическое удаление запрещено. |
| **I11** | После рестарта Router любая нетерминальная операция → `PAUSED_RECOVERY`; dispatch запрещён до принятия отчёта реконсиляции человеком; реконсиляция — read-only by construction. |
| **I12** | `job.COMPLETED` только если все операции терминальны в `{VERIFIED_OK, ADOPTED, SKIPPED}` и ноль `UNKNOWN`. |
| **I13** | В состояниях `PAUSED*` разрешён только whitelist read-only вызовов; всё остальное блокируется диспетчером инструментов. |
| **I14** | Unknown-класс ошибки = halt (fail closed). «Не знаю» ≠ «успешно». |

## 6. Рекомендуемый первый реальный write-test

### 6.1 Критерий выбора

Операция должна давать **максимально полный и независимый read-back**: несколько query-путей, не переиспользующих ответ create, с проверяемыми скалярными полями.

| Кандидат | Read-back | Вердикт |
|---|---|---|
| `create_wall` | тип+этаж+слой (фильтр), GUID, `GetDetailsOfElements` (геометрия, высота, толщина, слой), маркер через property API, счётчик — **4 независимых пути** | **Выбор №1** |
| `create_slab` | полигон + толщина + уровень + площадь; нет референсной линии, нет flip, нет авто-обрезки в стыках | **Выбор №2 / fallback** |
| `create_column` | просто, но не репрезентативно для контура дома | Нет |
| `create_window` / `create_door` | требует host-стену (зависимость), локальная система координат, зависимость от библиотечной части | **Нет** — не первый |
| `create_story` | структурная, двигает существующие элементы | **Нет** — не первый |
| `change` / `move` / `rotate` / `bulk` | вне scope v1 | Нет |

**Правило решения:** берём `create_wall`. Если в capability probe read-back стены окажется нестабильным в AC29, переключаемся на `create_slab` — он геометрически «чище» (нет reference line, flip и обрезки в стыках).

### 6.2 Рецепт первой стены

```
Проект:      одноразовая песочница, НЕ untitled, НЕ Teamwork, 1 инстанс Archicad
Этаж:        существующий, разрешённый по имени + отметке (не по индексу)
Предусловие: счётчик Wall на этаже == 0; слой существует, видим, не заблокирован
Изоляция:    нет других элементов в радиусе 3 м → стыки и обрезка исключены
Геометрия:   from [1.5, 2.5] → to [6.5, 2.5]   ← намеренно: x≠y, обе ≠0
             length 5.0 ≠ height 3.0 ≠ thickness 0.30  ← намеренно: все три различны
             Ось выровнена (угол 0) → угол проверяем без допуска на поворот
Настройки:   reference_line = center, base_level = 0.0, top_link = absolute
```

**Зачем именно такие числа:** координаты с `x≠y` и обе ненулевые детектируют подмену осей и знака; попарно различные length/height/thickness детектируют подмену полей местами. Симметричные «красивые» числа (0,0 → 12,0) скрывают ровно эти ошибки.

**Ожидаемый read-back (все 4 пути должны согласовываться):**

| Путь | Что проверяем |
|---|---|
| `GetElementsByType('Wall')` + фильтр этаж/слой | ровно 1 элемент |
| `GetDetailsOfElements` по GUID | from/to референсной линии, length 5.0, height 3.0, thickness 0.30, слой, этаж |
| Property API по GUID | маркер **строково равен** `BX:<job>:<object-id>:<nonce>` |
| Счётчик по типу | `Wall` +1 |

### 6.3 Последовательность прогонов

| # | Прогон | Критерий успеха |
|---|---|---|
| **T0** | Capability probe, **read-only**: проверить эмпирически все 5 инфраструктурных возможностей (M22) + носитель маркера (M6) | Таблица заполнена по факту, а не по документации. Если маркер не пишется или не читается — **стоп**, P0 #3 невыполним, нужен fallback |
| **T1** | Dry-run полного плана дома | 0 мутаций, отчёт по capability |
| **T2** | **Одна стена** по рецепту 6.2 | mapping `CONFIRMED`, все 4 пути согласованы, `count_delta` = +1, journal полный |
| **T3** | Инжекция: kill -9 Router между dispatch и записью маркера | `PAUSED(RECOVERY_REQUIRED)`; после reconcile — `ADOPTED` (или `MARKER_UNKNOWN` → reconcile); **второй стены нет** |
| **T4** | Инжекция: запись маркера принудительно fails | `MARKER_UNKNOWN` или `CREATED_UNBOUND`; объект в orphan registry; `count_delta` = +1; PAUSED |

| **T7** | Порча verify: подменить ожидаемую длину на 50.0 | `VERIFIED_FAILED` — проверка не «прощает» |

## 7. Go / No-Go

### 7.1 Инфраструктурный go (блокирующий)

- [ ] WAL: `INTENT` записан и fsync'нут **до** dispatch; journal переживает `kill -9` без пропусков seq
- [ ] Single-flight + singleton процесса подтверждены тестом (второй процесс не стартует; параллельный запрос не даёт второй dispatch)
- [ ] Персистентный idempotency key (T6 зелёный)
- [ ] `PAUSED*` + whitelist read-only (в PAUSED мутирующий вызов невозможен ни при каком пути кода)
- [ ] WriteGate по умолчанию OFF; нужен `confirm_token`

### 7.2 Capability go (блокирующий)

- [ ] Носитель маркера выбран **эмпирически** и round-trip подтверждён (E1/E3)
- [ ] Поиск по маркеру работает и **точный**, и **префиксный** (M7)
- [ ] Независимые пути read-back подтверждены: по GUID, по маркеру, по фильтру тип+этаж+слой, счётчик
- [ ] Для каждой op в scope v1 вычислен `sufficient verification set` и он непуст
- [ ] Проект: не untitled, не Teamwork, один инстанс

### 7.3 Go на первую стену

- [ ] T2: mapping `CONFIRMED`, 4 пути согласованы, `count_delta` +1, journal полный
- [ ] T3: после краха — `ADOPTED`, **второй стены нет**
- [ ] T4: orphan зарегистрирован, PAUSED, автоматического удаления не было
- [ ] T5: verify умеет падать
- [ ] T6: 0 дублей
- [ ] T7: verify не «прощает»

### 7.4 No-Go — немедленная остановка

- Маркер не пишется или не читается обратно, и нет подтверждённого fallback → **P0 #3 не реализуем в текущем виде**, переходить к write нельзя
- Read-back unavailable при работающем write (известный класс дефектов AC29) → не «продолжить без проверки», а **стоп до появления рабочего read-back**
- Любой наблюдаемый случай автоповтора мутации → стоп, это означает, что I2 не реализован
- Любой случай «PAUSED, но мутация всё равно ушла» → стоп

### 7.5 Только после этого — расширение

Второй тип элемента → пакет с зависимостью →PKG02 из 4 стен с T-стыком → проёмы (`host_wall`) → stories. Каждый шаг — с теми же критериями.
